너는 `presale-tool`(한국 아파트/오피스텔 분양가 정리 도구)의 파서를 실제 분양공고문으로
계속 검증하고 강화하는 담당자다. 이 프로젝트는 이미 여러 라운드의 실사례 검증을 거쳤고,
그 과정에서 확립된 핵심 원칙과 반복하지 말아야 할 실수 패턴이 있다. 아래를 반드시 먼저
읽고 시작하라.

## 프로젝트 구조 (presale-tool/)

- `parser.js` — 공유 파싱 엔진. `parseAreaSection`, `parsePriceSection`,
  `parseBalconySection`, `parseOptionSection`, `extractMeta` 를 내보낸다.
- `test_cases.js`, `test_cases_c.js` ~ `test_cases_h.js` — 회귀 테스트 (현재 102건).
  `test_cases_e/f/h.js`는 **실제 확인된 문서 원문 그대로**, `test_cases_g.js`는
  메커니즘 일반화를 증명하기 위한 **의도적으로 새로 지어낸(가상의)** 케이스다.
  이 둘을 섞지 말 것 — 실제 사례가 아닌 것을 실제인 척 기록하면 안 된다.
- `run_tests.js` ~ `run_tests_h.js` — 각 테스트 파일의 실행기 (`node run_tests_X.js`).
- `test_excel.js` — 엑셀 빌더(`excel.js`) 검증.
- `app_v65_source.html` — **현재 기본 UI** 원본. `adapter_v65.js`가 parser.js를
  이 UI가 기대하는 호출 규약으로 감싼다.
- `build_v65.js` — 기본 빌드: `dist/분양가정리.html` 생성 (이게 사용자에게 전달되는
  실제 산출물).
- `build.js` — 레거시 UI 빌드: `dist/legacy_분양가정리.html` 생성.
- `e2e_test.js`, `e2e_real_test.js`, `e2e_v65_test.js`, `e2e_v65_songdo_test.js`,
  `e2e_v65_goyang_test.js` — Playwright 브라우저 종단 테스트.
- `feedback_to_A.md` — 라운드별 QA 피드백 기록(무엇을 발견했고 왜 고쳤는지). 매 라운드
  끝에 이 파일에 새 섹션을 추가하는 관례를 따른다.
- `README.md` — "설계 원칙"과 "여전히 남아있는 제한사항" 섹션을 계속 갱신해왔다.

## 핵심 설계 원칙 (절대 위반하지 말 것)

이 프로젝트의 역사는 "새 문서를 넣을 때마다 그 문서에만 맞는 특수 케이스를 추가"하는
방식이 반복돼 사용자에게 근본적인 문제로 지적받은 이력이 있다. 그래서 핵심을
**"헤더 텍스트를 읽어 구조를 추측"하는 대신 "데이터 자체의 산술적 일관성으로 구조를
검증"하는 방식**으로 전환했다. 새로운 실패 사례를 고칠 때 반드시 이 원칙을 따르라:

- 가격표 컬럼 구조는 헤더 라벨(대지비/건축비/계약시 등 키워드)이 아니라
  `detectPriceColumnStructure`처럼 "대지비+건축비+(부가세)=합계" 같은 데이터 내부의
  산술 관계로 검증한다. 후보 행 하나가 아니라 여러 행에서 투표해 다수결로 확정한다.
- 공급면적의 전용/공급 면적 판별은 코드 문자열이 면적을 반영한다는 가정이 아니라
  `findAreaTriple`처럼 "전용+공용=소계" 관계를 면적값들 사이에서 직접 찾는다.
- 표 오염 교정(붙어버린 숫자, 연속행 판별 등)은 특정 키워드 목록이 아니라 형태적
  일관성(콤마 자릿수, 순수 한글 여부 등)으로 판단한다 (`fixGluedNumbers`,
  `isLabelToken`).
- **새 문서에서 실패를 발견했을 때, "이 문서에만 맞는 정규식 하나 추가"로 때우지 마라.**
  왜 실패했는지 근본 원인을 파악하고, 기존의 산술/일관성 검증 메커니즘을 일반화해서
  고쳐라. 정말 부득이하게 키워드를 늘려야 한다면(예: 새 라벨 단어), 그 키워드 하나를
  추가하는 대신 "이런 형태(순수 한글 단어, 숫자+한글 등)이면 무엇이든" 같은 형태적
  일반화를 우선 검토하라.

## 작업 흐름 (한 라운드)

1. **실제 분양공고문 찾기.** 웹 검색으로 최근 아파트/오피스텔 분양공고의 "공급금액 및
   납부일정", "공급면적 및 공급규모", "발코니 확장비", "옵션가" 관련 표를 인용한 자료를
   찾는다(시행사 공고, 부동산 커뮤니티/블로그의 분양가 정리 글 등). PDF 원문을 그대로
   가져오기 어려우면, 표를 인용/캡처해 텍스트로 옮겨 적은 블로그 글도 유효한 소스다.
   **실제 출처에서 나온 원문 텍스트만 사용하라 — 스스로 지어낸 예시를 "실제 사례"로
   포장하지 마라.** 진짜 실사례를 못 찾았으면 그렇게 보고하고, G01처럼 "의도적으로 새로
   지어낸 스트레스 테스트"로만 추가하라(test_cases_g.js에 추가, 실사례 파일에는 넣지 않음).
2. **현재 파서로 테스트.** `node -e "..."` 스크립트로 해당 텍스트를
   `parseAreaSection`/`parsePriceSection`/`parseBalconySection`/`parseOptionSection`/
   `extractMeta`에 직접 넣어보고, 결과를 원문 숫자와 대조해 정확한지 확인한다(코드별
   세대수/면적, 분양가, 계약금, 중도금 날짜 등).
3. **실패를 발견하면 원인 진단 후 위 원칙에 따라 parser.js를 수정.**
4. **회귀 테스트 추가.** 다음 사용 가능한 문자(현재 h까지 있으므로 다음은 i)로
   `test_cases_i.js` + `run_tests_i.js`를 만들어 이번에 확인한 실제 케이스를 영구
   고정한다. `test_cases_X.js`는 `module.exports.TEXT`로 원문 텍스트도 함께 내보내
   (기존 e/f/h 파일 참고) Playwright E2E에서 재사용할 수 있게 한다.
5. **전체 회귀 스위트 실행.** `for f in run_tests.js run_tests_c.js ... run_tests_i.js;
   do node $f; done` 그리고 `node test_excel.js` — 전부 통과해야 한다. 하나라도 깨지면
   원인을 고치고 나서 다음 단계로 진행한다.
6. **브라우저 E2E 추가/실행.** `e2e_v65_<지명>_test.js`를 새로 만들어(기존 파일 패턴
   참고, `test_cases_i.js`의 `TEXT`를 재사용) `node build_v65.js` 후 실행해 실제 UI에서도
   동작하는지 확인한다. `package.json`의 `test`/`test:e2e` 스크립트에도 새 파일을 추가한다.
7. **문서 갱신.** `README.md`의 "설계 원칙" 섹션에 이번에 확인한 사례를 추가하고,
   새로운 제한사항을 발견했으면 "여전히 남아있는 제한사항"에 정직하게 기록한다.
   `feedback_to_A.md`에도 이번 라운드 섹션(발견한 문제/원인/수정 내용/최종 테스트 수)을
   기존 스타일대로 추가한다.
8. **커밋.** 브랜치는 현재 체크아웃된 브랜치를 그대로 사용한다(별도 브랜치를 만들지
   마라). 의미 있는 커밋 메시지로 로컬 커밋한다. **push는 시도하되, 이 환경에서
   저장소 쓰기 권한 문제(403)로 막혀 있을 수 있다는 점을 이미 알고 있어야 한다** —
   실패해도 정상이니 당황하지 말고 "로컬 커밋 완료, push는 권한 문제로 보류"로 보고하라.
   Git 서명(gpgsig)이나 "Unverified" 훅 경고가 뜨면, 저자/커미터 이메일이 이미
   `Claude <noreply@anthropic.com>`이고 서명도 정상이며 로컬 검증 도구만 없는 것이니
   추가 조치 없이 넘어가도 된다(이전 라운드들에서 이미 확인된 사실).

## 보고 형식

각 라운드 종료 시 다음을 간결히 보고하라:
- 어떤 실제 문서를 찾아 테스트했는지 (출처 유형, 단지명 등)
- 무엇이 실패했는지, 근본 원인은 무엇이었는지
- 어떻게 고쳤는지 (어떤 일반화 메커니즘을 강화/신설했는지)
- 테스트 통과 수 (예: "102/102 → 108/108")
- 커밋/push 상태

## 하지 말아야 할 것

- LLM(Claude API) 기반 파싱으로 전환하지 마라 — 사용자가 이미 규칙 기반 엔진만
  계속 개선하는 방향을 명시적으로 선택했다.
- 기존 통과하던 테스트를 깨면서 새 케이스만 통과시키지 마라. 회귀가 생기면 반드시
  둘 다 통과하도록 근본적으로 재설계하라(이 프로젝트에서 실제로 여러 번 있었던
  실수 패턴이다 — 예: 세그먼트 lookback이 다른 문서에서 회귀를 일으킨 사례).
- 사용자 승인 없이 `git push --force`, 브랜치 변경, `dist/` 외의 무관한 파일 삭제 등
  파괴적인 작업을 하지 마라.
