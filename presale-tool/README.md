# 분양가 정리 도구

한국 분양공고(공급면적/공급금액/발코니확장비/에어컨옵션가) 텍스트를 파싱해
분양가를 정리하고 마스터 엑셀로 출력하는 단일 HTML 웹앱. 텍스트를 직접 붙여넣는
대신 **분양광고 PDF를 첨부하면 브라우저에서 바로 텍스트를 추출해 4개 입력란을
자동으로 채워주는 기능**도 지원한다(텍스트 기반 PDF만 해당, 아래 "PDF 첨부 자동인식"
참고).

## 구조

프론트엔드는 두 벌이 있다. **`app_v65_source.html` 기반이 현재 기본(canonical) UI**이고
(`npm run build`가 이걸 조립한다), `app.html`/`logic.js` 기반은 초기 버전으로 남겨뒀다
(`npm run build:legacy`). 파서/엑셀 엔진(`parser.js`)은 두 UI가 공유한다.

## 실행

```bash
npm install              # xlsx/exceljs/pdfjs-dist(테스트용), playwright(E2E용)
npm test                 # 파서 115/115 + 엑셀 빌더 + PDF 추출 파이프라인 검증
npm run test:e2e         # 브라우저 종단 테스트 (기본 UI + 레거시 UI + PDF 첨부 + 엑셀 스타일/입력필드, 합성/실제 데이터)
npm run build            # dist/분양가정리.html 생성 (기본 UI, app_v65_source.html 기반)
npm run build:legacy     # 레거시 UI로 다시 빌드하고 싶을 때만 사용
```

`dist/분양가정리.html`은 외부 리소스 없이 그대로 브라우저에서 열어 사용할 수 있는
단일 파일 산출물이다.

## 데이터 흐름

1. 입력 탭에서 4개 섹션 텍스트를 붙여넣고 `parseAreaSection`으로 주택형/코드 목록을 얻는다.
   공급대상표가 여러 주택형을 포함해 통째로 한 줄(개행 없이 이어짐)로 붙여넣어져도, 코드
   토큰(관리코드/약식표기)을 경계로 삼아 각 주택형 구간을 분리해 인식한다.
2. 그 코드 목록을 `parsePriceSection` / `parseBalconySection` / `parseOptionSection`에
   전달해 코드 표기 형식(관리번호/호형/숫자만 등)에 관계없이 정확히 매칭한다.
   - `parsePriceSection`은 **헤더를 먼저 읽어 컬럼맵을 만드는 방식이 기본 동작**이다.
     "대지비 건축비 (부가세) 합계/소계/계 계약시 <날짜×6> 입주시"처럼 헤더가 각 컬럼의
     의미를 명시하면, 그 순서 그대로 데이터 컬럼을 매핑한다. 코드/동호수가 매 행마다
     반복되지 않고 이어지는(carry-forward) 실제 공고문 표도, 표 전체가 개행 없이 한
     줄로 이어져 있어도 정확히 행 단위로 분리된다. 이 헤더 컬럼맵을 못 찾을 때만
     레거시 방식(금액 크기 추정)으로 폴백한다.
3. 결과를 `unit.types[].rows[]` 구조로 합쳐 상태에 저장한다 (localStorage 보조,
   JSON 내보내기/불러오기가 주 저장 수단).
4. 엑셀 다운로드 시 `unit` 배열을 순회하며 `buildBlock`을 반복 호출해 하나의 시트에
   단지별 블록을 이어붙인다.

## PDF 첨부 자동인식

텍스트를 직접 복사해 붙여넣는 대신, 분양광고 **PDF 파일을 통째로 첨부**하면 4개
입력란을 자동으로 채워준다. 서버/네트워크/LLM 없이 전부 브라우저 안에서 끝나며
(`vendor/pdfjs.min.js` = Mozilla `pdf.js` legacy 빌드가 `app_v65_source.html`에
직접 인라인돼 있고, 워커도 Blob URL로 구성해 외부 파일 의존이 없다), "오프라인
단일 HTML 파일" 원칙은 그대로 유지된다.

1. **텍스트 추출** (`extractPdfFullText`): `pdfjsLib.getDocument`로 각 페이지의
   `getTextContent()` 아이템을 **그대로 이어붙이고 `hasEOL`일 때만 개행을 삽입**한다.
   흔히 하는 실수(아이템 사이에 무조건 공백을 끼워 넣는 방식)로 하면 "구분"이
   "구 분"처럼 매 음절마다 공백이 끼어드는 문제가 생긴다 — pdf.js가 이미 필요한
   공백/줄바꿈을 자체 아이템으로 정확히 계산해서 내려주므로, 그 위에 임의로 더
   추가하지 않는 것이 핵심이다.
2. **섹션 자동 분리** (`parser.js`의 `splitDocumentSections`): 추출된 문서 전체
   텍스트에서 "■"(U+25A0) 또는 "▣"(U+25A3) 불릿으로 시작하는 섹션 제목("공급대상
   및 공급규모", "공급금액 및 납부일정", "분양가격 납부조건 등 안내", "발코니 확장",
   "추가선택 옵션품목" 등)을 앵커로 삼아 공급면적/공급금액/발코니/옵션 4개 구간의
   경계를 찾는다. 실제 문서 디스클레이머 불릿은 "⦁"/"•" 등 다른 문자를 쓰므로
   섞이지 않는다. **문서 전체를 통째로 파서에 넣지 않고 반드시 섹션을 먼저 분리하는
   이유**: 전체 원문을 그대로 `parseAreaSection`에 넣어보면 무관한 페이지의 숫자가
   우연히 코드/면적 패턴처럼 보여 거짓 행이 섞여 들어가는 사례를 실제로 확인했다
   (예: 본문 어딘가의 "84G ... 0.2 ... 1.2"가 우연히 유효한 삼항관계로 보여 가짜
   타입으로 인식됨). 섹션을 먼저 좁혀야 이런 오염을 피할 수 있다.
3. 섹션을 못 찾은 항목은 건드리지 않고 비워두므로, 사용자가 해당 입력란만 직접
   붙여넣기로 채우면 된다. 공급면적 섹션은 찾았지만 실제로 0건이 파싱되면(문서
   레이아웃 문제로 표가 다른 섹션과 뒤섞였을 가능성) 별도 경고를 띄운다.

**지원 범위와 한계**
- 텍스트 레이어가 있는 PDF만 지원한다. **스캔 이미지 PDF(텍스트 레이어 없음)는
  추출 자체가 안 된다** — OCR이나 비전 LLM이 필요한데, 전자는 촘촘한 숫자표에서
  부정확할 위험이 크고 후자는 서버/네트워크/비용이 발생해 "규칙 기반, 오프라인
  단일 파일" 원칙과 상충하므로 현재는 지원하지 않는다.
- pdf.js의 텍스트 추출은 항상 시각적 순서와 100% 일치하지 않는다. 복잡한
  다단/중첩 표 레이아웃에서는 표 하나의 데이터가 물리적으로 다른 표의 헤더
  뒤로 재배치돼 나오는 경우가 실제로 관찰됐다(더샵 송도그란테르 G5-3 PDF에서,
  "▣ 공급대상" 제목 바로 뒤에는 안내문만 남고 실제 표 본문 전체가 "▣ 공급금액
  및 납부일정" 제목 뒤로 밀려나 두 표가 하나의 섹션으로 합쳐진 사례). 사용자가
  실제로 이 문서를 첨부해 공급면적이 인식되지 않는 것을 확인해줘서, `(단위 :
  ㎡...)`(면적표 고유 표기)와 `(단위 : 원...)`(가격표 고유 표기)가 항상 각자 표
  바로 앞에 붙어 있다는 점을 2차 경계로 삼아 `splitDocumentSections`가 자동으로
  재분리하도록 일반화했다(`repairMisplacedAreaTable`). **이전에 폐기했던 "실패하면
  두 섹션을 합쳐서 통째로 재시도"하는 폴백과는 다른 메커니즘이다** — 그 폴백은
  구분자 없이 area+price 전체를 한꺼번에 `parseAreaSection`에 밀어 넣어 무관한
  숫자가 섞여 들어가는 조용한 오염을 일으켰지만, 이번 복구는 각 표 고유의 단위
  표기로 경계를 정확히 잘라낸 뒤 그 결과가 실제로 유효한 면적 행을 만들어낼
  때만(`parseAreaSection(...).length > 0`) 채택하고, 그렇지 않으면 조용히 포기해
  기존 동작(안내문만 남은 area 섹션)으로 되돌아간다 — 명시적 실패가 조용한
  오염보다 안전하다는 원칙은 그대로 유지된다. 이 복구로도 안 되는 재배치 패턴이
  있을 수 있으므로, 자동 채움 후에는 항상 분석 칩(표기N/합산M)을 확인하고
  필요하면 직접 수정해야 한다.
- 한 PDF 파일에 서로 다른 두 개의 분양공고(예: 아파트+오피스텔)가 함께 들어있는
  경우, 섹션 앵커는 "문서 순서상 첫 번째로 나오는" 것을 채택한다. 두 번째
  공고를 채우려면 필요한 페이지만 별도 PDF로 잘라서 첨부하거나, 직접 붙여넣어야
  한다.
- **좌표(x/y) 기반 표 재구성은 실험했으나 채택하지 않았다.** pdf.js가 글자
  조각마다 좌표(`item.transform`)를 함께 주므로, "읽기 순서로 이어붙이기" 대신
  y좌표로 줄을 묶고 x좌표로 줄 안 순서를 정하는 방식을 프로토타입으로 만들어
  실사례 PDF 3건(fixtures/*.pdf) 전부에 돌려봤다. 더샵 송도그란테르 G5-3의
  "제목/표 재배치" 문제는 해결됐지만(`▣ 공급대상` 바로 뒤에 실제 표가 정상적으로
  옴), **같은 문서의 가격표에서 새로운 회귀가 발생**했다 — 엑셀/HWP에서 내보낸
  PDF는 세로 병합 셀(예: "84OA 2"가 층별 2개 행에 걸쳐 있는 셀)의 텍스트를 병합
  범위의 세로 중앙에 배치하는 경우가 많은데, 순수 y좌표 정렬은 이 라벨을 자신이
  속한 두 행 "사이"에 끼워 넣어버려 코드 캐리포워드 파싱이 깨졌다. 시화MTV·
  힐스테이트 둔산 문서에서도 각각 다른 지점(콤마 층 목록, 특정 가격 행)에서
  같은 유형의 회귀가 나타나 3건 전부에서 최소 하나씩 실패가 발생했다 — 즉 이
  방식은 "재배치" 버그 하나를 고치는 대신 "세로 병합 셀" 버그를 새로 만들어내는
  트레이드오프였다. 병합 셀을 올바르게 처리하려면 열 단위 클러스터링과 셀의
  세로 범위(span) 추정까지 필요한, 훨씬 더 큰 표 재구성 알고리즘이 필요하다고
  판단해 이번에는 보류했다. 기존 `repairMisplacedAreaTable`(단위표기 2차 경계
  복구)가 이미 실사례로 검증된 안전한 해법이므로 그대로 유지한다. 회귀 없이
  검증 가능한 더 정교한 설계가 나오면 재검토한다.

### 20차: 실사례 5건(의왕역 SK VIEW/부산 장안지구 B-2블록/춘천 리버뷰 아이파크/오산헤리티지자이 1·2단지) 추가 검증

사용자가 "지금 제대로 인식을 못 한다"며 실제 PDF 5건을 직접 업로드했다(전부
민영 아파트, 2026년 7월 청약Home 표준 양식). poppler-utils를 새로 설치해
Read 도구로 PDF 페이지를 실제 이미지로 렌더링해 원문과 직접 대조하는 방식을
처음 도입했고(그동안은 pdf.js 텍스트 추출 결과만 보고 구조를 추정해야
했다), presale-doc-hunter 에이전트로 5건을 순서대로 처리해 발견한 실패를
전부 일반화된 방식으로 고쳤다.

- **레터 접미사형과 무접미사 관리코드형이 한 표에 섞임** (의왕역 SK VIEW) —
  기존 `LONG_CODE_RE`(`084.9750A`처럼 문자 접미사 필수)는 "36 45"처럼 동/호
  구분이 필요 없어 접미사가 아예 없는 타입(`036.9653`)을 코드로 인식하지
  못했다. 이런 무접미사 값은 순수 면적값과 형태가 똑같아 정규식만으로는
  구분할 수 없으므로, "이 값이 몇 토큰 뒤 전용면적으로 그대로 반복 등장하는지"
  자기참조로 검증하는 `findSelfConsistentBareCodeBoundaries`를 추가했다.
- **"합계" 행 뒤 부가 표(주택형 표시 안내 등)가 코드를 다시 나열** (의왕역 SK
  VIEW, 부산 장안지구) — 이 재등장이 세그먼트 경계에 섞이면 마지막 타입의
  구간이 합계 행과 부가 표까지 통째로 삼켜버렸다. "합계" 행 이후에 나오는
  경계는 전부 걸러내도록 고쳤다.
- **부가세 면제 행의 "-" 표기** (의왕역 SK VIEW, 오산헤리티지자이) — "대지비+
  건축비+부가세=합계" 산술 검증이 부가세 칸의 "-"(숫자가 아님)에서 막혀
  컬럼 구조 자체를 못 찾았다. 금액 자리에서만 "-"를 0으로 취급하도록
  일반화했다(다른 판별에는 영향 없음).
- **표 중간에 안내문이 끼어들어 뒷부분 행이 밀려남** (부산 장안지구) — pdf.js
  재구성 순서상 "■ 공통사항" 안내문이 표 중간에 끼어들어 59B 후반부/84A/84B
  행이 그 뒤로 밀렸다. area 섹션에서 이미 확인된 코드 중 price 섹션에서
  하나도 못 찾은 코드가 있는지(=표가 잘렸는지)로 감지하고, 그 코드가 다시
  등장하는 뒷부분을 찾아 이어붙이되 실제로 코드 커버리지가 개선될 때만
  채택하는 `repairFragmentedPriceTable`/`repairFragmentedAmountSection`을
  추가했다(발코니/옵션 섹션도 같은 문제를 겪을 수 있어 공용으로 만듦).
- **"공고일은 ~습니다" 서술형 문장** (부산 장안지구) — 라벨과 값 사이에 한글
  조사가 끼는 문장 형태를 `extractMeta`가 놓쳤다.
- **번호 매김/단위표기 소제목으로 나뉘는 다항목 옵션 카탈로그** (춘천 리버뷰
  아이파크, 의왕역 SK VIEW) — "1) 시스템에어컨 2) 가전 3) 인테리어" 또는
  "천장형 시스템에어컨(단위: ...) / 시스템 공기청정기(단위: ...)"처럼 서로
  다른 품목이 여러 소제목으로 나뉘면, "코드당 최솟값 하나"라는 기존 스캔
  전제로는 품목을 구분할 방법이 없어 전혀 다른 품목의 최저가가 섞였다. 어느
  품목이 "그" 옵션가인지 판단할 근거가 없으므로, 첫 소제목만 남기고 나머지는
  명시적으로 포기하도록 했다(뒤섞인 값보다 첫 품목만 정확한 쪽이 안전).
- **"구분 84A 84B ... 비고"류 타입별 열거 카탈로그 표** (의왕역 SK VIEW) —
  품목(행)마다 타입별 금액이 열로 나열되는 표는 "코드 하나에 값 하나"라는
  전제와 근본적으로 다르다. 이런 표가 섞여 있으면 스캔에서 제외하되
  (`stripCatalogTables`), 그 표가 섹션의 유일한 내용일 때는(=다른 정상 표가
  없을 때만) 헤더-데이터 열 정렬이 정확히 대응하는지 검증해 값을 복구한다
  (`extractColumnAlignedCandidates` - 오산헤리티지자이 발코니 확장비 표에서
  이 폴백이 실제로 쓰였다).
- **"84B,D"처럼 숫자 접두부를 생략한 코드 나열** (오산헤리티지자이 1단지) —
  같은 접두부(84)를 공유하는 코드를 나열할 때 뒤쪽 코드의 숫자 접두부를
  생략하는 표기를 지원했다.
- **불릿(■/▣) 없이 줄 시작 문구만으로 된 대분류 제목** (오산헤리티지자이
  1·2단지) — "공급대상 및 면적"/"공급대금 및 납부일정"처럼 불릿이 전혀
  없는 문서를 위해 줄 시작(`^`) 앵커를 추가했다.
- **번호만 붙고 불릿 없는 옵션 대분류 제목** (의왕역 SK VIEW) — "8 추가
  선택품목(유상옵션)" 다음에 오는 첫 "■"/"▣"(=실제 표 헤딩)를 앵커로 쓰도록
  `findChapterFirstHeading`을 추가했다.
- **섹션 종료 경계 오탐** — "납부일정"이 표 제목 자체에도 흔히 쓰여
  (`공급금액 및 납부일정`, `발코니 확장 공사비 및 납부일정`) 종료 경계로
  오인하면 표 헤딩 바로 다음에서 잘려버렸다. "납부계좌/납부방법/유의사항/
  안내사항"처럼 표 제목으로는 안 쓰이는 안내문 특유 표현만 종료 경계로 쓰도록
  `findSectionEndHeading`으로 좁혔다.

`test_cases_m.js`(10건, M01~M10)가 이 원문 발췌 기반 회귀를 고정하고,
`test_pdf_extract.js`에도 15건 추가(16→31건). `e2e_v65_uiwang_pdf_test.js` 등
새 실사례 5건 각각 PDF 첨부 → 분석 → 엑셀 다운로드까지 전체 플로우를
Playwright로 돌려 엑셀 결과값이 원문과 일치하는지까지 검증한다. 전체 회귀
스위트 재실행 결과 회귀 없음.

### 21차: "정정" 공고문 2건 + 원본 1건(부산에코델타 디에트르 더 퍼스트, 북수원이목지구 리체Ⅰ·Ⅱ) 추가 검증

사용자가 "정정 전/정정 후 옵션 대조표"가 앞에 붙은 **정정 공고문**을 처음 업로드했다.
이전까지 다룬 문서는 전부 원본(비정정) 공고문이었기 때문에, "정정 전"(구버전, 틀린
금액)이 조용히 채택될 위험을 가장 먼저 점검했다 — 결과적으로 `splitDocumentSections`가
area→price→balcony→option을 문서 앞에서부터 순차적으로 찾는 기존 설계 덕분에, 정정
대조 블록이 언제나 본문보다 앞쪽에 있는 이 문서들에서는 **별도 방어 코드 없이도
"정정 전" 값이 섞여 들어오지 않았다**(회귀 테스트 N01/P07로 고정). 대신 이 3건에서
새로운 실패 6가지를 발견해 고쳤다.

- **옵션 섹션 앵커에 "사항"이 낀 표현** (부산에코델타 디에트르 더 퍼스트) — "■ 추가선택
  옵션품목"만 지원하던 기존 앵커가 "■ 추가선택**사항** 옵션품목"에는 걸리지 않아 옵션
  섹션 전체를 놓쳤다. 키워드를 하나씩 추가하는 대신 "■/▣ 바로 뒤 추가 + (순수 한글/공백
  6자 이내) + 옵션품목" 형태 자체를 앵커로 일반화했다.
- **공급대상 표 데이터 행 뒤에 코드만 다시 나열하는 매핑 표** (부산에코델타) — "■ 주택형
  표시 안내"(주택형 037.9750A ↔ 약식표기 84A 같은 대조표)의 코드 재나열이 세그먼트
  경계로 중복 채택돼, 마지막 실제 데이터 행의 세그먼트가 매핑 표까지 통째로 삼켜
  세대수가 오염됐다. "코드 바로 다음이 소수 면적값인 occurrence만 실제 데이터 행"이라는
  구조적 차이로 중복 경계를 제거하도록 `parseAreaSection`을 고쳤다.
- **공급대상 표가 페이지 경계를 넘어가며 부분/전체가 가격 섹션 쪽에 놓임** (부산에코델타:
  일부만 누락, 북수원이목지구 리체Ⅰ: 전체 누락) — 여러 안내문 뒤로 나머지 타입 행이
  가격표 제목보다도 앞쪽에 끼어 있는 문서였다. "행 번호+긴 코드로 시작하는 행"이라는
  구조를 앵커로 삼아 원래 자리(마지막 데이터 행 바로 뒤)에 되돌려 끼워 넣는
  `repairFragmentedAreaTable`을 신설하고, "(단위 : ㎡...)" 표기 자체가 없어 기존
  `repairMisplacedAreaTable`의 마커 기반 복구가 안 통하는 전체 누락 케이스까지 같은
  함수 하나로 일반화했다.
- **공급금액표가 약식표기 없이 긴 코드로만 주택형을 구분** (부산에코델타) — 공급면적표는
  "84A" 약식표기를 쓰지만 공급금액표는 "084.9944A" 긴 코드로만 표기해, 약식표기
  목록만으로는 가격표의 행을 하나도 못 찾았다. 긴 코드의 정수부(앞자리 0 제거)+말미
  문자를 약식표기와 대조하는 산술적 변환(`longCodeToShortCandidate`)으로 별칭을
  인식했다.
- **가격 섹션 앵커가 "공급금액 표"처럼 짧게 줄어든 표현** (북수원이목지구 리체Ⅰ·Ⅱ) —
  "및 납부일정"/"납부조건 등 안내" 없이 그냥 "표"만 붙는 문서가 있어 가격 섹션 전체를
  못 찾았다. 이 과정에서 자바스크립트 정규식의 `\b`가 한글 앞뒤에서는 성립하지 않는다는
  것도 발견했다(`/표\b/`가 "표" 바로 뒤에 아무것도 없어도 조용히 매칭 실패) — "다음
  글자가 한글이 아니면"으로 대체했다.
- **층 표기와 세대수 숫자가 괄호로 묶인 동/호 설명 때문에 서로 다른 줄에 떨어짐**
  (북수원이목지구 리체Ⅰ·Ⅱ) — "10층(최상층 119동 4,5호, ...)"처럼 층 표기 자체에
  괄호가 붙거나, "최상층\n(107동 2,3호,\n108동 1,2호)\n4 ..."처럼 층 표기 다음
  토큰부터 새로 괄호가 열리는 행에서, 괄호 안 동/호 토큰이 세대수 숫자를 새 층
  목록으로 오인시켜 세대수가 유실됐다. `skipFloorPrefix`의 괄호 흡수를 "이미 열려
  있거나 다음 토큰이 새로 여는 경우"로 넓히고, 표 복구용 `repairUndercountedPriceRows`
  에는 층 표기와 세대수 숫자가 아예 다른 줄로 갈라진 경우까지 대응하는
  `mergeWrappedFloorLines`(괄호 제거 후 재확인으로 괄호 안 동/호 번호 오매칭 방지)를
  신설했다. 이 김에 "최상층"/"최하층"처럼 숫자 접두부 없이 단독으로 쓰이는 층
  구분값도 복구용 정규식들이 인식하도록 넓혔다(본문 토크나이저는 이미 관대했는데
  복구용 정규식들만 더 엄격했던 불일치 해소).
- **동일 층, 다른 동/호 그룹의 세대수 숫자만 페이지 경계로 고립** (북수원이목지구
  리체Ⅱ) — "1층 (동/호 목록1) 4 .../ (동/호 목록2) 10 ..."처럼 같은 층에 동/호
  그룹만 다르고 층 표기 자체는 반복되지 않는 행에서, 동/호 목록이 페이지 경계를
  넘어가며 세대수 숫자 "10"만 남아 새 층 목록으로 오인됐다(세대수 1로 기본값 처리).
  "바로 직전 토큰이 동/호 목록의 일부였다"는 문맥 신호가 있으면 그 토큰을 세대수로
  먼저 시도해보는 분기를 `scanPriceRowsWithMap`에 추가했다.
- **옵션 카탈로그가 페이지 경계에서 끊기고 헤더 재인쇄 뒤 코드가 재출현** (북수원이목지구
  리체Ⅱ) — "84A"/"84AP"처럼 다락(복층)세대 타입이 나란히 있는 문서에서, "84B ...
  (페이지 경계, 헤더 재인쇄) ... 84BP ..."처럼 84B의 카탈로그가 페이지 경계에서
  끊기고 다음 페이지에 "84BP"가 다시 나오는 경우를 새 타입으로의 전환으로 오인해,
  84B는 페이지가 끊기기 전 항목의 (더 비싼) 값만 최저가로 잘못 채택하고 정작 더
  저렴한 항목들은 전부 84BP에게만 돌아갔다. "비고사항"/"비고"로 끝나는 표 헤더 직후에
  코드가 다시 나오면 새 그룹이 아니라 직전 그룹이 계속된다는 신호로 보고, 직전

`test_cases_n.js`(8건, N01~N08, 부산에코델타)/`test_cases_o.js`(6건, O01~O06, 리체Ⅰ)/
`test_cases_p.js`(7건, P01~P07, 리체Ⅱ)가 이 원문 발췌 기반 회귀를 고정한다.

### 23차: 사용자가 새로 올린 실사례 5건 - "PDF는 인식되는데 타입별로 전환이 안 된다" 문제 재현/해결

사용자가 22차(엑셀 재작성)와 함께 "새로 올리는 문서들이 PDF 인식은 되는데 그 내용이
타입별 분양가/확장비 등으로 전환이 안 된다"는 문제를 제기했지만, 당시엔 재현 가능한
구체적 파일이 없어 다루지 못했다. 이후 사용자가 실사례 5건(PDF)을 첨부하며 "체크"를
요청해, 실제 Playwright로 각 문서를 첨부→분석까지 돌려보며 원인을 추적했다.

**진단**: 5건 중 3건(부산 장안지구/춘천 리버뷰/오산헤리티지자이 계열)은 이미 정상
동작했고, 나머지 2건에서 실패 패턴을 발견했다. 특히 "봉선동 르 오네뜨 2차"(광주광역시
남구) 문서는 타입 인식 자체가 완전히 깨져 있었다("130A1"/"130A2" 두 타입이 "130"
하나로 뭉개지고, 중도금 회차가 0/6으로 통째로 버려짐) - 이게 사용자가 말한 "전환이
안 된다"의 실제 사례였다.

- **약식표기가 표 셀 줄바꿈으로 코드 중간에서 쪼개짐** — "130A1"이 PDF 원본 표에서
  "130"과 "A1"이 서로 다른 줄에 걸쳐 있어(칸이 좁아 줄바꿈), 텍스트 추출 시 둘 사이에
  공백만 남아 별개 토큰("130", "A1")이 됐다. 코드 인식 정규식(`SHORT_CODE_RE`)은 한
  토큰 안에서만 매칭하므로 이 상태로는 아예 코드로 인식되지 않고, 숫자만 남는 최후수단
  규칙(코드가 없을 때 인접 정수를 코드로 대신 쓰는 폴백)으로 넘어가 "130A1"/"130A2"가
  둘 다 "130"이라는 잘못된 코드로 뭉개지며 세대수도 나중에 나온 값(26)이 먼저 값(28)을
  덮어썼다. `reglueSplitShortCodes()`를 새로 추가해, "숫자 토큰 바로 뒤에 문자(+숫자)
  접미부 토큰이 오고 합친 결과가 SHORT_CODE_RE와 일치하며, 근처에 그 숫자 접두부와
  정수부가 같은 실수(전용면적 등, 실제로 이 숫자가 그 타입의 코드라는 증거)가 있을 때만"
  두 토큰을 하나로 재결합한다(우연한 숫자+글자 나열까지 잘못 합치지 않도록 구조적 근거를
  요구). `parseAreaSection`의 토크나이즈 직후에 적용했다.
- **발코니/옵션 섹션 소제목이 대괄호형** — "① 천장형 시스템에어컨 [단위 : 원, VAT
  포함]"처럼 대괄호를 쓰는 문서인데, 여러 소제목(품목 대분류) 중 첫 번째만 남기고
  나머지는 버리는 기존 로직(`restrictToFirstUnitMarkerSubsection`, 20차에서 도입 -
  이미 "오산헤리티지자이" 실사례로 검증된 규칙)이 괄호("(단위: ...)")만 인식하고
  대괄호는 인식하지 못했다. 그 결과 첫 소제목 뒤에 이어지는 완전히 무관한 두 번째
  소제목("개별 선택옵션" - 코드 없이 품목만 나열되는 카탈로그)의 값이 코드에 잘못
  섞여 붙었다. 괄호/대괄호 둘 다 인정하도록 정규식을 넓혔다.
- **"구분" 헤더의 두 글자 사이 공백** — 같은 문서에 "계 약 금"/"중 도 금"처럼 PDF
  추출 시 한글 단어 중간에 공백이 끼는 문제가 카탈로그형 표 판별 키워드 "구분"에도
  나타나("구 분"), `stripCatalogTables`/`extractColumnAlignedCandidates`가 해당
  표를 인식하지 못했다. 공백 유무와 무관하게 인식하도록 정규식을 넓혔다(다만 이 문서의
  "구분" 표는 코드 목록이 "구분" 줄이 아니라 바로 다음 줄에 있는 특수한 배치라, 이
  변경만으로는 해당 표가 완전히 복구되지는 않는다 - 아래 "남은 제한사항" 참고).
- **130A1/130A2가 무작위 배정으로 가격표를 통째로 공유** — 사용자가 "130A1과 A2가
  동일한 분양가로 나온 거야, 둘이 같아"라고 직접 확인해줬다(공고문 원문에도 두 타입이
  같은 주택형 130.0926에 속하고 "무작위 배정되오니"라고 명시돼 있었다). 처음엔
  "코드가 나란히 언급되면 공유"라는 형태 신호로 접근했다가 기존 회귀 스위트 2건이
  깨졌는데(H03의 별칭 충돌, O04의 단순 매핑 안내문), 판단 근거를 **"이 코드가 가격
  섹션 전체에서 정확히 한 번만 등장하는가"**로 바꾸니 세 사례가 전부 안전하게
  갈렸다 — 진짜 공유 그룹의 코드는 공유 지점 딱 한 번만 나오는 반면, 별칭 충돌/매핑
  안내문의 코드는 나중에 자기 이름의 데이터 블록을 또 갖기 때문이다. `scanPriceRowsWithMap`에
  반영해 130A1/130A2 둘 다 같은 6개 층별 행(세대수 합계 54)을 정확히 공유하게 됐다.

**검증 방법**: 실제 PDF를 Playwright로 첨부→분석까지 돌려(파서를 거치지 않고) 원문과
직접 대조했다. `test_cases_q.js`(7건, Q01~Q07, 봉선동 르 오네뜨 2차 원문 발췌 기반)로
회귀를 고정했다. `npm test`/`npm run test:e2e` 전체 재실행 결과 회귀 없음.

**여전히 남아있는 제한사항**: "천장형 시스템에어컨" 옵션처럼 "구분 [코드 열 나열은
헤더 다음 줄] / 품목명 / 타입별 금액..." 형태로 코드가 "구분" 줄이 아니라 그 다음
줄에 열거되는 카탈로그(실사례: 오산헤리티지자이 계열 문서 중 1건)는 기존
`stripCatalogTables`/`extractColumnAlignedCandidates`가 "코드가 헤더 줄 자체에
있어야 한다"고 전제하고 있어 여전히 인식하지 못하고, 표 안 첫 값이 모든 타입에
동일하게 채워진다(분양가/확장비 등 핵심 항목은 영향 없고, 옵션 하나의 표기만
부정확 - 심각도가 낮아 이번 라운드에서는 다루지 않았다). 재현 가능한 문서가 있으니
다음 라운드에서 "코드가 헤더 다음 줄에 나열되는 카탈로그" 케이스로 일반화해 고칠 것.

### 24차: 진월동지역주택조합 - 페이지 경계에서 타입 하나가 통째로 유실되는 문제

23차에서 5건을 체크한 뒤 사용자가 별도로 여섯 번째 문서(진월동지역주택조합 신축공사)를
제보하며 "페이지 넘어가는 부분을 인식 못해서 평형에 맞게 인식이 안 됐다"고 원문 발췌를
직접 붙여넣어줬다. 이 문서는 공급금액표가 84D 타입 중간(페이지 8→9 경계)에서 끊기고,
pdf.js 재구성 순서상 그 사이에 완전히 무관한 "■ 특별공급 공급세대수" 표와 "■ 공통
유의사항" 안내문 여러 줄이 끼어든 뒤에야 84D의 마지막 행("14층\n(최상) 1
338,283,000...")과 115 타입의 코드 헤더("115 109동 1호, 2호")가 이어졌다.

이런 "표 중간에 무관한 섹션이 끼어드는" 문제 자체는 20~21차에서 이미 여러 건 다뤄봤고
전용 복구 로직(`repairFragmentedPriceTable`/`repairUndercountedPriceRows`)도 있었지만,
이번엔 그 복구 로직 자체에 있던 두 가지 결함이 겹쳐 복구가 실패했다:

- **`mergeWrappedFloorLines`의 판단 순서가 거꾸로였다** — "14층\n(최상) 1
  338,283,000..."처럼 층 표기와 실제 숫자 사이에 괄호 부연설명이 완전히 가로막고 있으면,
  괄호를 지우기 전(원문 그대로)에는 "층" 바로 뒤가 공백이 아니라 "("라 **영원히**
  매칭될 수 없다. 그런데 이 함수는 "원문이 이미 매칭돼야" 그다음에 괄호를 지운 버전도
  확인하는 순서였다 - 원문이 매칭될 수 없는 이 경우엔 괄호 제거 버전 확인 자체를 못 가보고
  항상 실패했다. 판단을 괄호 제거 버전 하나로 단순화했다(괄호 안 내용은 지워지고 없으니
  "괄호 안 숫자에 우연히 매칭"될 걱정도 자연히 사라진다).
- **`repairFragmentedPriceTable`의 재개 지점 탐색 정규식이 너무 좁았다** — "층 표기 바로
  뒤에 공백만 있고 곧장 숫자가 오는" 한 줄짜리 패턴만 인정해서, 위 병합 함수를 고쳐 한
  줄로 합쳐놔도 "14층 (최상) 1 338,283,000..."처럼 괄호가 포함되면 여전히 매칭되지
  않았다. 그러면 이 줄을 건너뛰고 그다음(엉뚱하게 더 늦은) 매칭인 "1층 2
  359,530,000..."(115의 첫 데이터 행)에서 재개해버려, 건너뛴 84D의 마지막 행과 그 사이의
  "115 109동 1호, 2호" 코드 헤더가 통째로 사라졌다. 그 결과 115의 네 행은 코드 없이
  이어지다 직전 코드(84D)에 잘못 흡수되어(84D는 9세대인데 16세대로 과다집계, 115는
  아예 0/8) 진단됐다. `repairUndercountedPriceRows`가 이미 쓰고 있던 "층 표기 뒤에
  숫자·개행만 아니면 무엇이든(괄호 부연설명 포함) 허용"하는 정규식으로 통일했다.

**검증 방법**: 사용자가 첨부한 실제 PDF를 Playwright로 첨부→분석까지 돌려 원문과 직접
대조했다(84A~84D/115/126 여섯 타입 전부 표기 세대수와 정확히 일치하는지). 원인이 두
복구 함수의 정규식/판단 로직 자체에 있었으므로, 같은 로직을 쓰는 기존 실사례
(부산에코델타시티/북수원이목지구 등, `repairFragmentedPriceTable`·
`repairUndercountedPriceRows`·`mergeWrappedFloorLines`를 이미 쓰던 문서)가 회귀하지
않는지도 전체 스위트로 재확인했다. `test_cases_r.js`(6건, R01~R06, 진월동지역주택조합
원문 발췌 기반) 신설. `npm test`/`npm run test:e2e` 전체 재실행 결과 회귀 없음.

### 26차: 목동윤슬자이 오피스텔 + 송도국제도시 B1블록 대방디엠시티 오피스텔 - "안됌"

사용자가 PDF 두 건을 첨부하고 "안됌"이라고만 남겼다. 두 문서를 앱 파이프라인에 직접
넣어보니 `splitDocumentSections`가 area/price 앵커를 아예 못 찾아 `ta-area`가 계속
비어 있는(느린 게 아니라 애초에 아무것도 안 쓰는) 상태였다. 목동윤슬자이 오피스텔(서울
양천구)에서는 4가지, 송도국제도시 B1블록 대방디엠시티 오피스텔(인천 연수구)에서는
3가지 실패를 발견해 전부 일반화된 방식으로 고쳤다.

- **"공급면적"/"납부 일정" 헤딩 문구 변형** - area 앵커가 "공급대상"류만, price 앵커가
  공백 없는 "납부일정"만 인식해 이 문서의 "■ 공급면적 및 공급규모"/"■ 공급금액 및
  납부 일정"(글자 사이 공백)을 놓쳤다. 두 앵커 모두 패턴을 넓혔다.
- **하이픈+숫자 접미사 코드** - "117C-T1"/"118C-T2" 등 5개 타입이 `SHORT_CODE_RE`의
  하이픈 접미사 그룹(문자만 허용)에 안 걸려 인식 자체가 안 됐다. 숫자까지 허용하도록
  넓혔다.
- **총계행 뒤 별개 요약표가 세대수를 오염** - area 표가 진짜 총계행으로 끝난 뒤, 같은
  코드를 재나열하는 별개의 "■ 거주자 우선 분양" 표가 자기 "합계" 행으로 끝나면, 기존
  "마지막 경계 이후"라는 총계행 판별 기준이 뒤쪽 요약표 쪽으로 잘못 밀려 두 표 경계가
  뒤섞이고 특정 타입 세대수가 두 배로 집계됐다. "모든 코드가 최초로 한 바퀴 다 나온
  시점" 기준으로 바꿔 진짜 표의 총계행에서 정확히 멈추도록 고쳤다.
- **"최저가/최고가" 두 행짜리 가격 범위 표(세대수 컬럼 없음)** - 층별 행 없이 타입마다
  "최저가"/"최고가" 딱 두 행만 있고 세대수 칸조차 없는 신규 구조라, 기존 로직이 세대수
  1로 기본 처리해 타입당 2세대로 심하게 과소집계됐다. 처음엔 두 값을 항목별 평균한 행
  하나로 합쳤으나, 사용자 확인에 따라 이 업계 관행대로 전체 세대수를 절반씩(홀수면
  나머지 1세대는 최고가 쪽) 나눠 각자 실제 가격을 갖는 두 행으로 분리하도록 수정했다
  (소계/평균 행은 기존처럼 세대수 가중평균 수식이라 결과적으로 두 가격의 가중평균이
  반영된다).
- **번호+")" 옵션 챕터 헤딩** - "1) FCU / 2) 추가선택사항 옵션품목 / 3) 추가선택사항
  유의사항"처럼 번호 뒤 괄호와 "사항" 삽입어가 있는 변형을 옵션 챕터 정규식이 못 받았다.
  기존 관대한 사이 구간 패턴을 재사용해 넓혔다.
- **옵션 챕터가 실제 표를 통째로 건너뜀** - 위를 고쳐도, 챕터 헤딩 뒤 "다음 ■/▣ 헤딩까지
  무조건 건너뛰기"가 문서 훨씬 뒤의 무관한 헤딩까지 건너뛰어 표 자체를 옵션 섹션에서
  빠뜨렸다. 챕터 헤딩 바로 뒤에 같은 목차의 형제 번호줄이 이어지면 그 목차 블록 끝까지만
  건너뛰도록 고쳤다(형제 줄이 없는 기존 사례는 그대로 다음 실제 헤딩까지 건너뜀).
- **옵션 표 뒤 별개 카탈로그가 마지막 타입 옵션가를 오염** - 옵션 표 바로 뒤에 코드
  반복 없이 "전 주택형" 공통 품목만 나열되는 가전/가구 카탈로그가 이어지면, "코드
  마지막 등장 뒤 한글 단어는 그 코드의 연속행"이라는 규칙이 이 무관한 카탈로그에도
  적용돼 마지막 타입의 옵션가가 엉뚱한 값으로 뭉개졌다. "타입"과 "품목명"이 나란히
  컬럼 헤더로 나오는 줄이 보이면 그 지점부터는 별개의 표로 보고 그 이전까지만 남기도록
  고쳤다.

**검증 방법**: 두 실제 PDF를 Playwright로 첨부→분석까지 돌려 원문과 대조했다(목동윤슬자이
11개 타입, 송도 대방디엠시티 2개 타입 전부 표기 세대수와 정확히 일치). 총계행/옵션
챕터 헤딩 로직을 쓰는 기존 실사례(진월동지역주택조합, 춘천 리버뷰 아이파크,
부산에코델타시티)가 회귀하지 않는지도 전체 스위트로 재확인했다. `test_cases_s.js`
(9건, S01~S09, 두 문서 원문 발췌 기반) 신설. `npm test`/`npm run test:e2e` 전체
재실행 결과 회귀 없음.

### 27차: 전남광주통합특별시 북구 임동 아파트 - "새 분양공고 올릴 때마다 다 안된다"

사용자가 새 PDF를 첨부하며 "새 분양공고를 올릴 때마다 다 안 된다"고 강하게 제보했다.
실제로는 area/price 앵커 자체는 정상 인식됐지만(구조적 실패 없음), 24개 타입 중
다수가 표기 세대수와 어긋나거나 가격이 아예 0으로 잡히는 4가지 실패가 겹쳐 있었다.

- **총계행 뒤 이전 행 값이 다음 코드에 들러붙음** - "195 5103A2"처럼 area 표에서 이전
  행의 마지막 숫자(최하층우선배정세대수)가 PDF 재구성 순서상 다음 하위코드 앞에 공백
  없이 붙어 "5103A2"라는 존재하지 않는 코드로 잘못 인식되고, 진짜 103A2가 통째로
  유실됐다(103B2/112A2/128A2도 동일). "주택형은 X1, X2, X3로 구분되며"라는 각주가
  명시적으로 나열하는 진짜 하위코드 목록을 근거로, 그 코드 바로 앞 숫자만 띄어 쓰도록
  고쳤다(각주에 실제로 선언된 코드만 대상으로 삼아 다른 문맥의 우연한 조합은 건드리지
  않음).
- **통합청약 패밀리(하위코드 3개가 청약 단계에서 하나로 묶임)** - "103.0590A 주택형은
  103A1, 103A2, 103A3로 구분되며 ... 통합하여 접수"처럼, 가격 표에 긴 코드
  ("103.0590A")가 한 번만 나오고 그 뒤로 코드 표시 없는 동일 구조 블록이 하위코드
  개수만큼 반복되는 문서가 있었다. 긴 코드가 "103A"까지만 좁혀지고 어느 하위코드도
  정확히 못 가리켜 기존엔 세 하위코드 전부 가격이 0으로 인식됐다. codeSet 안에서
  "숫자+문자 접두부가 같고 끝자리 숫자만 다른" 코드가 2개 이상이면 패밀리로 인정해,
  긴 코드를 첫 하위코드로 열고 나머지를 대기열에 둔 뒤, 층 표기가 처음 값으로
  되돌아오는 시점(예: "45~49층"까지 다 돌고 다시 "2~4층"이 나옴)에 다음 하위코드로
  넘어가도록 했다(동 목록이 페이지 경계에서 끊겨 블록 중간에 다시 나오는 경우와 진짜
  새 블록의 시작을 구분해야 했는데, 동 토큰 재등장 자체를 신호로 쓰면 페이지 경계
  케이스에서 오탐이 실측으로 확인돼, 더 안정적인 "층 표기 한 바퀴" 신호로 교체).
- **area 표의 패밀리 총계는 하위코드 개별값이 아니라 합산값** - 위를 고쳐 가격 섹션은
  정확해져도(103A1=77/103A2=73/103A3=73), area 표의 "223"은 셋을 합친 값 하나뿐이라
  표기 세대수 자체는 여전히 부정확했다. 패밀리의 가격 섹션 합산 세대수 총합이 area에
  실제로 나타나는 값과 정확히 일치할 때만(우연이 아니라는 산술적 증거가 있을 때만)
  area의 패밀리 구성원 전원의 표기 세대수를 가격 섹션 기준의 정확한 값으로 교체하는
  `reconcileFamilyAreaUnits`를 신설해, area 파싱→가격 파싱이 끝난 뒤 앱단에서 호출했다.
- **긴 소수형 관리코드가 줄바꿈에서 마지막 숫자 한 자리만 잘림** - "200.476\n8B" ->
  "200.4768B"처럼, 코드가 줄바꿈 지점에서 소수점 뒤 마지막 숫자(+문자 접미사)만 다음
  줄로 잘려나가는 경우가 있었다. 이러면 코드 인식이 실패해 가격 데이터가 유실되거나
  (통합청약 패밀리의 마지막 하위코드처럼) 직전 코드에 잘못 흡수됐다(실측: 이 오염으로
  128A3 세대수가 31 대신 35로 과다집계). 소수점 뒤 자릿수가 하나 부족한 토큰 바로 뒤에
  "숫자+문자" 토큰이 이어지고, 합쳤을 때 정확히 유효한 코드 형태가 될 때만 재결합했다.

**검증 방법**: 사용자가 첨부한 실제 PDF를 Playwright로 첨부→분석까지 돌려 원문과
대조했다(24개 타입 중 22개가 표기 세대수와 정확히 일치하는 것으로 정상화 - 나머지
2개(214A/214D)는 이 문서에서 발견된 또 다른 별개 문제로, 최상층 특화(펜트) 세대의
가격 데이터가 문서 훨씬 뒤 "■ 공통 유의사항" 섹션 안에 흩어져 있어 옵션 섹션으로
잘못 분류되는 중이라 이번엔 고치지 못했다 - 가격 0으로 명시적으로 표시되어 알아채기
쉬우므로 다음 라운드 과제로 남긴다). `test_cases_t.js`(7건, T01~T07, 이 문서 원문
발췌 기반) 신설. `npm test`/`npm run test:e2e` 전체 재실행 결과 회귀 없음.

### 27차 후속: 남겨뒀던 214A/214D(최상층 특화 펜트 세대)까지 마저 수정

사용자가 "마저 고쳐줘"라고 요청해, 27차에서 다음 라운드 과제로 남겼던 마지막 2개
타입도 이어서 고쳤다.

- **문서 뒤쪽의 두 번째 "■ 공급금액 표"** - "최상층 특화(펜트)세대 : 200B, 207F, 209C,
  211E, 214A, 214D"만 다루는 별도 가격 표가 balcony/option 앵커보다도 늦게, "■ 주택형
  표시 안내"(코드 매핑 표)와 "■ 공통 유의사항" 대분류 섹션 안에 흩어져 있었다. 이 두
  번째 표는 200B~211E 가격을 메인 표와 중복해서 다시 보여주기도 해서, 통째로 이어붙이면
  그 타입들의 세대수가 두 배로 잘못 집계된다. 그래서 표 전체를 붙이는 대신, 기존 복구를
  다 거치고도 여전히 가격 행이 하나도 없는 코드(214A/214D)만 targeted로 찾는다. area
  섹션에서 이미 읽어낸 전용면적으로 그 코드의 온전한 긴 코드 문자열을 재구성해(예:
  "214A" + 전용면적 214.6183 -> "214.6183A"), 그 문자열이 실제로 다시 등장하는 지점부터만
  잘라 붙였다. 코드 매핑 표에 같은 긴 코드가 줄바꿈 없는 온전한 형태로 먼저 나와 헷갈릴
  수 있어(디코이), 첫 번째가 아니라 마지막 occurrence를 쓰도록 해서 실제 줄바꿈으로
  쪼개진 진짜 가격 행("214.618\n3A ...")을 정확히 찾게 했다.
- **각주 프로즈가 두 타입 사이에 낄 때 세대수 오염** - area 표에서 214A와 214D 사이에
  "• 평형환산방법 : 공급면적(㎡) × 0.3025 또는 ÷ 3.3058"처럼 소수값이 섞인 각주가
  통째로 끼면, "면적값 뒤 첫 정수"를 찾는 세대수 추출 로직이 그 각주의 소수값들 때문에
  기준점이 밀려 엉뚱한 값(1 대신, 다음 타입의 관리번호 "16")을 잘못 채택했다. "•"로
  시작하는 각주는 데이터 행에 나올 수 없는 형태이므로, 세그먼트를 그 지점 이전까지로
  잘라 각주가 아예 안 섞이게 했다.

**검증 방법**: 같은 실제 PDF를 Playwright로 재검증해 24개 타입 전부(84A~128A3,
200B~214D) 표기 세대수와 정확히 일치함을 확인했다. `test_cases_t.js`에 T08/T08b/T09
(3건, 두 번째 표의 디코이 회피·중복 방지·각주 오염 방지) 추가(총 10건). `npm test`/
`npm run test:e2e` 전체 재실행 결과 회귀 없음.

## 엑셀 내보내기 스타일/구조

사용자가 제공한 실제 참고 엑셀(부동산 매입 검토용 정리본)을 직접 뜯어보고 발견한
격차를 반영했다.

- **SheetJS 커뮤니티판은 셀 스타일을 저장하지 않는다** — 가장 근본적인 원인이었다.
  `app_v65_source.html`의 `buildBlock`이 폰트/배경색/테두리 스타일 객체를 지정하고
  있었는데도, 실제로 다운로드된 xlsx의 `styles.xml`을 열어보면 커스텀 폰트/배경색/
  테두리가 전혀 기록돼 있지 않았다(기본 Calibri 폰트 하나뿐). SheetJS(`xlsx` 패키지)의
  스타일 **쓰기**는 유료 Pro 버전 전용 기능이라, 커뮤니티판은 스타일 객체를 조용히
  버린다(에러 없음). 행 높이(`rh`)도 같은 이유로 계산은 되지만 실제로 워크시트에
  적용하는 코드가 없어 버려지고 있었다. 스타일 쓰기를 지원하는 **ExcelJS**(MIT
  라이선스)로 엑셀 생성 부분만 교체해 해결했다(`vendor/exceljs.min.js`, xlsx.js/pdf.js와
  같은 방식으로 인라인). 레거시 UI(`app.html`)의 `excel.js`는 SheetJS를 그대로 쓰며
  이 문제가 남아있지만, 참고용으로만 유지되는 UI라 우선순위가 낮다.
- **아파트/오피스텔 평당가 산정 기준이 구분되지 않았다** — 아파트는 공급면적
  기준(공급평수 = 공급면적×0.3025), 오피스�텔은 전용면적 기준(전용평수 =
  전용면적×0.3025)으로 분모 자체가 다른데, `buildBlock`이 `unit.kind`와 무관하게
  항상 공급면적 기준으로만 계산하고 있었다. 오피스텔 결과의 평당가 전체가 실제보다
  낮게(계약면적이 전용면적보다 크므로) 나오는 문제였다. `kind`에 따라 C열 계산식과
  헤더 라벨(공급면적/공급평수/공급세대수 ↔ 계약면적/전용평수/공급호실수)을 모두
  분기하도록 고쳤다.
- **같은 평형대 여러 타입을 묶은 집계 행이 없었다** — 참고 엑셀은 타입별 소계
  외에, 약식표기 앞자리 숫자가 같은 타입들(예: "84A"+"84B")을 다시 가중평균한
  "84합계" 같은 행을 추가로 넣어 비교를 돕는다. 이 중간 집계 레벨이 아예 없어서
  타입이 여러 개인 평형대는 서로 비교하기 어려웠다. 코드의 숫자 접두부로 그룹을
  묶어 타입 소계와 전체 합계 사이에 그룹 합계 행(초록색 배경)을 추가했다(전체
  합계 자체는 참고 엑셀과 마찬가지로 이 그룹 행이 아니라 타입별 소계에서 직접
  집계 — 그룹 행은 참고용 중간 집계일 뿐 계산 경로에 끼지 않는다).
- **테두리 스타일이 전혀 없었다** — 타입 경계, 헤더 하단, 합계 상하단을 구분하는
  테두리가 코드에 아예 없어 위 스타일 문제와 겹쳐 시각적 구획이 전혀 없었다.
  헤더(위 medium/아래 thin), 타입 시작행(위 thin), 소계·그룹합계(위아래 thin),
  전체합계(위 thin/아래 medium)로 참고 엑셀과 동일한 위계를 부여했다.
- **청약 경쟁률(특별공급/1순위/2순위 접수건수)·계약 진행 현황(일자별 계약 건수,
  잔여, 분양률)·청약일정 텍스트 컬럼은 헤더만 있고 값을 채우는 로직이 없었다** —
  이 데이터는 애초에 분양공고 원문에는 없고 분양 진행 중 실시간으로 갱신되는
  정보라, 파서가 채울 수 없다. **수정 탭에 타입별 입력 필드를 추가**해(특별공급/
  1순위/2순위 당해·기타 접수건수, 계약 1~5일차 건수, 비고, 청약일정등 텍스트)
  사용자가 직접 입력하면 저장 시 엑셀에도 반영되도록 했다. 합계·경쟁률·계약총계·
  잔여·분양률은 참고 엑셀과 동일하게 입력값이 아니라 수식(`SUM`, 나눗셈)으로
  계산한다. 타입별로 선택 입력이라, 입력하지 않은 타입은 억지로 0을 채우지 않고
  엑셀에서도 그대로 빈 칸으로 남는다(`실사례 조작 금지`와 같은 결의 원칙 - 모르는
  값을 지어내지 않는다).

`e2e_v65_excel_style_test.js`가 다운로드한 xlsx를 ExcelJS로 다시 읽어 스타일/구조
항목들이 실제 파일에 기록됐는지(값이 아니라 `styles.xml` 자체) 검증하고,
`e2e_v65_subscription_fields_test.js`가 수정 탭에서 입력한 청약/계약 현황 값과
수식이 정확히 반영되는지, 입력하지 않은 타입은 여전히 빈 칸인지 검증한다.

### 17차: 계약 진행 현황 열 삭제 + 중도금 이자 표 재배치 + 사이드바 다중 선택

사용자가 "수정 전/후" 실사용 서식 예시 두 개(같은 단지, 63열 구버전 vs 38열
정리본)를 함께 제공해, openpyxl로 두 파일을 셀 단위까지 비교해 반영했다.

- **계약 1~5일차/계약총계/잔여/분양률/청약일정등(구 AC~AK, 16개 열)을 완전히
  삭제했다** — 분양 진행 중에나 의미 있는 값이라 정리 단계에서는 불필요하다는
  판단. Excel 열뿐 아니라 더는 어디에도 쓰이지 않는 "수정" 탭의 계약 일차/
  청약일정등 입력 필드(`e-cd0~e-cd4`, `e-sched`)와 그 값을 읽고 쓰던 코드
  (`saveEdit`, `doAdd`의 타입 객체 초기화)도 함께 제거했다(비고 입력 필드는
  그대로 남아 있음 — AB열은 삭제 대상이 아니다).
- **중도금 이자 계산 표(금리·회차별 납부일·일수)를 청약 현황 블록(1~28열)
  바로 옆, AE(금리)~AL(입주일) 위치로 옮겼다** — 구버전은 BD~BK(56~63열)에
  멀리 떨어져 있었다. 열 번호를 하드코딩 라벨 배열이 아니라
  `RATE_COL/DATE_COL0/MOVEIN_COL` 상수 + `colLetter()`로 계산해, 나중에 다시
  옮기더라도 상수만 바꾸면 되게 했다. 실사용 서식 예시를 보면 이 블록은 회차
  값이 비어 있어도(중도금 회차가 6회 미만인 실사례) 6칸 모두 사방 thin 상자
  테두리를 그린다 — 데이터 유무와 표 모양(칸 개수)을 분리했다.
- **T(특공당해)열 왼쪽/AB(비고)열 오른쪽에 medium 굵기 구획선이 헤더부터
  합계 행까지 표 전체 높이를 관통해 이어진다** — 청약 현황 블록(20~28열)의
  좌우 경계를 시각적으로 분리하는 선으로, 실사용 서식 예시를 열 단위로 훑어
  발견했다. 헤더 행(6/7행)은 이 구획선이 헤더 자체의 상하 테두리와 겹쳐서
  나타나고, 본문/소계/그룹합계 행은 medium 한 줄만, 합계 행(마지막 행)은
  거기에 bottom:medium까지 더해진다 — 행 종류별로 조합이 달라 `sideBd()`
  헬퍼로 "그 칸에 필요한 서식에 구획선만 덧붙이기"를 통일했다.
- **A~E(전용면적~약식표기, 타입당 한 번만 값이 있는 칸)를 타입의 층행 범위
  전체로 세로 병합한다** — 구버전은 층행마다 반복 표기했지만, 실사용 서식
  예시는 한 타입 안에서 값이 같은 칸을 병합해 보기 편하게 만든다. 병합
  상자 안에서도 매 층행 아래쪽에는 thin 구분선이 이어지고, 상자 맨 위(첫
  층행)에만 thin 선이 추가로 걸린다(중간/마지막 행은 위쪽 선 없음) — 이
  패턴은 openpyxl로 층행이 다른 여러 타입을 대조해 확인했다.
- **ExcelJS 병합 셀 서식 버그를 우회했다** — 병합된 셀 중 마스터가 아닌
  슬레이브 셀에 나중에 다시 서식을 쓰면, 마스터 셀의 서식까지 함께 사라지는
  경우가 있었다(헤더 6:7행 병합에서 AB6의 위쪽 테두리가 사라지는 회귀로
  발견). 헤더 6:7행 병합은 두 행 모두 서식을 다 쓴 "뒤"에 걸도록 순서를
  바꿔 해결했다(A~E 세로 병합과 동일한 순서 원칙 - 값/서식을 먼저 쓰고
  병합은 마지막에).
- **엑셀 다운로드에서 여러 단지를 한 번에 선택해 내보낼 수 있다** — 사이드바
  트리의 단지/지역/전체 지역 앞에 체크박스를 추가해(`exportSelectedIds`,
  기존 "상세보기 중인 단지 하나"만 내보내던 `selId`와는 별개 상태), 지역
  체크박스를 누르면 그 지역 산하 모든 단지가 함께 선택된다. 체크된 단지가
  있으면 그것들만, 하나도 없으면 기존 동작(상세보기 중인 단지 하나, 그것도
  없으면 전체)대로 내보낸다.

`e2e_v65_excel_restructure_test.js`가 실제 실사례(더샵 송도그란테르 G5-3블록)
PDF로 다운로드한 xlsx를 검증한다(삭제된 열, 이동한 이자 표 위치와 상자 테두리,
T/AB열 구획선, A~E 세로 병합, 새 열 너비/행 높이). `e2e_v65_excel_style_test.js`와
`e2e_v65_subscription_fields_test.js`, `e2e_v65_meta_interest_fix_test.js`도 새
열 위치(AE~AL) 기준으로 갱신했다.

### 18차: 요약 탭 평당가 기준 불일치 + "수정 탭 저장 시 중도금 실납부액이 사라지는" 회귀

사용자가 "요약 탭에서 오피스텔 평당가가 계약면적 기준으로 나온다"와 "이자후불제인데
왜 엑셀에 중도금이 반영 안 되냐"고 제보해 추적한 뒤 고친 두 가지 버그.

- **요약 탭(`renderSummary`)의 평당가가 `unit.kind`와 무관하게 항상
  `t.supply_area` 기준이었다** — 13차/17차에서 엑셀 내보내기(`buildBlock`)는
  이미 "아파트=공급면적, 오피스텔=전용면적" 기준으로 고쳤는데, 요약 탭은 별도
  계산 경로라 그 수정이 반영되지 않은 채 남아 있었다. 오피스텔은 `t.supply_area`
  필드가 실제로는 계약면적(엑셀 헤더 라벨도 "계약\n면적")이라, 요약 탭 숫자가
  엑셀 결과보다 낮게 표시됐다. `t.exclusive_area` 기준으로 통일하고, 타입
  헤더의 면적 표기도 오피스텔은 "전용 X㎡ (N평) · 계약 Y㎡", 아파트는
  "전용 X㎡ · 공급 Y㎡ (N평)"로 어느 값이 평당가 분모인지 드러나게 했다.
  "수정" 탭의 면적 입력 라벨도 같은 기준으로 갱신(오피스텔은 "공급면적"이
  아니라 "계약면적"으로 표시).
- **"수정" 탭에서 저장(`saveEdit`)할 때마다 회차별 중도금 실납부액
  (`row.mid_amounts`, 파서가 원문 공급금액표에서 읽어온 값 - 엑셀 중도금
  이자 계산의 원금으로 쓰임)이 통째로 사라졌다** — `saveEdit`이 `t.rows`를
  편집 테이블의 DOM 입력칸(동/층/세대/분양가)만으로 다시 만들면서, 그 입력칸
  자체가 없는 `mid_amounts`를 그냥 버렸다. 그 결과 **단지를 등록한 뒤 수정
  탭에서 무엇을 고치든(금리를 바로잡거나, 이자 조건을 "이자 후불제"로
  명시하거나, 비고를 입력하거나) 저장 버튼을 한 번이라도 누르면 그 단지의
  엑셀 중도금 이자가 전부 0으로 빠졌다** - "이자후불제인데 중도금이 반영 안
  된다"는 제보의 실제 원인이었다(이자 조건 자체의 판정 로직은 처음부터
  정상이었다). 같은 (동, 층) 값으로 기존 행의 `mid_amounts`를 이어받도록
  고쳤고, 행을 중간에서 삭제해 DOM 인덱스가 밀려도(인덱스가 아니라 동/층
  내용으로 매칭하므로) 엉뚱한 행에 잘못 붙지 않는다. 원문에 없던 새 행을
  사용자가 직접 추가한 경우는 매칭될 원본이 없으니 그대로 빈 배열(이자 0) -
  모르는 값을 지어내지 않는다는 원칙 그대로다.
- **부수 발견**: "수정" 탭에서 중도금 납부일을 手동 입력할 때 정확히 6개가
  아니면 통째로 무시하는 별도 검증(`if (dates.length===6)`)이 있었다 -
  6회 미만 문서(2회/4회/5회 등)를 수정 탭에서 고치면 조용히 무시되던 부분을
  doAdd의 최초 등록 로직과 같은 기준(1개 이상이면 반영)으로 통일했다.

`e2e_v65_summary_interest_fix_test.js`가 오피스텔 요약 탭 평당가(전용면적
기준), 저장 후에도 `mid_amounts`가 보존되는지(이자후불제로 조건을 바꾸고
저장해도 엑셀 이자 수식이 0으로 빠지지 않는지), 행 삭제 후에도 내용 기준
매칭이 안전한지를 검증한다.

### 19차: 소계/합계 행 전체 배색 + 전 셀 가운데 정렬 + 청약현황 블록 테두리 보강 + 단지명 배경색 종류별 분리

사용자가 엑셀 서식을 더 다듬어달라고 요청한 네 가지.

- **소계/평형합계/합계 행이 값이 없는 칸까지 A~S(1~19열) 전체에 끊김 없이
  배경색이 채워진다** — 예전엔 라벨(A열)·세대합계(H열)·가중평균(I~S열)이
  있는 칸에만 색이 있고 사이사이(B,D~G열 등)는 흰 칸으로 비어 있어 "줄무늬"
  처럼 보였다. `fillSummaryRow()` 헬퍼로 세 행 종류(소계=노랑, 평형합계=
  초록, 합계=하늘색) 모두 A~S를 먼저 통째로 칠하고, 그 위에 라벨/수식이
  들어가는 특정 칸을 다시 값과 함께 쓰는 순서로 정리했다(같은 테두리를
  다시 쓰므로 시각적으로 달라지지 않는다).
- **소계 행에도 평당가 분모(C열, 전용평수/공급평수)를 채운다** — 평형합계·
  합계 행은 이미 여러 타입을 가중평균한 C열 값을 보여주는데, 소계 행만
  비어 있었다. 한 타입 안에서는 C열이 항상 상수(A~E가 세로 병합되는 이유와
  같음)라 가중평균 수식 대신 그 타입 첫 행의 C열을 그대로 참조하게 했다
  (`=C{첫행}`).
- **청약현황 블록(20~28열) 중간(21~27열, 경쟁률 포함)에도 소계/합계 행의
  위/아래 테두리가 이어진다** — 그 블록은 A~S와 별개 구획이라 배경색은
  칠하지 않지만, 예전엔 테두리도 전혀 없어 "경쟁률 칸 아래가 뻥 뚫려
  보이는" 문제가 있었다. T(20)열 왼쪽/AB(28)열 오른쪽의 medium 구획선(표
  전체를 관통하는 전용 칸)은 그대로 두고, 그 사이 21~27열에만 나머지 열과
  같은 상/하 테두리를 이어줬다.
- **모든 셀을 가로+세로 가운데 정렬한다** — 그런데 코드는 처음부터
  `vertical:'center'`를 쓰고 있었는데, **ExcelJS는 세로 정렬 값으로
  `'center'`가 아니라 `'middle'`을 요구한다** - `'center'`를 넘기면 유효성
  검사에서 조용히 걸러져(`알 수 없는 값 -> undefined`) 세로 정렬 속성
  자체가 파일에 기록되지 않았고, 그러면 Excel은 진짜 기본값인 "아래쪽
  정렬"로 그렸다. 코드만 봐서는 정상으로 보이는 함정이라, 실제로 저장된
  파일을 다시 읽어(styles.xml) `vertical` 값이 있는지까지 확인하고서야
  발견했다. `AC` 정렬 상수를 `vertical:'middle'`로 고치고, `setCell`이
  정렬을 명시적으로 안 받은 호출(테두리만 채우는 호출 등)에도 기본값으로
  `AC`를 적용하도록 해 "모든 셀"이 실제로 가운데 정렬되게 했다.
- **단지명 제목 배경색을 아파트/오피스텔로 분리했다** — 오피스텔은 자주
  (강조4) 40% 더 밝게, 아파트는 주황(강조6) 40% 더 밝게. Office 2007-2010
  테마의 강조4(`8064A2`)/강조6(`F79646`)에 Excel의 "N% 더 밝게" 공식
  (`새값 = 원값×(1-tint) + 255×tint`, tint=0.4)을 적용해 `FFB3A2C7`/
  `FFFAC090`을 계산했다.

`e2e_v65_excel_style_test.js`에 관련 검증(S16~S23: 소계/평형합계/합계 행
전체 배색, 소계 C열 값, 경쟁률 칸 아래 테두리, 세로 가운데 정렬이 실제
`styles.xml`에 기록됐는지, 단지 종류별 제목 배경색)을 추가했다.

### 22차: 실사용 참고 파일(양주5,6차 당사매입부지) 기준 엑셀 내보내기 전면 재작성 + 청약현황 블록 삭제

사용자가 "엑셀 내보내기가 개판이다, 첨부한 파일을 참고해서 위치/레이아웃/색상/
수식/내용/프로그램 연계를 하나하나 확인하고 학습해서 이후 분양광고를 올렸을 때
동일한 형태로 결과물이 나오게끔 재작성해"라고 요청하며 실사용 참고 파일(의정부역
센트럴 아이파크 등 5개 단지가 담긴 "당사매입부지" 정리본)을 새로 제공했다. 이
파일은 17차에서 이미 반영했던 이전 참고 파일(송도그란테르 예시)과 열 구성이
달라(청약일정등 열이 다시 있고, 이자표 위치도 다름) 어느 쪽을 기준으로 삼을지
먼저 확인했고, 사용자는 새 파일을 최종 기준으로 지정했다. 이어서 사용자가 새
파일의 "특별공급/1·2순위/계/비고/청약일정등"(T~AC) 열 구성 스크린샷을 직접
첨부하며 "이 부분 다 삭제, 필요없어"라고 지정해, 그 블록 전체(구 청약 현황
블록)를 삭제 대상으로 확정했다.

**openpyxl로 참고 파일을 셀 단위까지 뜯어본 뒤** `buildBlock()`을 전면
재작성했다(값뿐 아니라 `cell.border`/`cell.fill`/`cell.alignment`/
`ws.merged_cells`/열너비/행높이까지 확인 — ExcelJS로 저장 파일을 다시 읽으면
병합 슬레이브 셀이 마스터 서식을 그대로 반사하는 함정이 있어, 이번에도
openpyxl로 실제 XML에 저장된 값을 기준으로 삼았다).

- **청약 현황 블록(구 T~AC: 특별공급/1·2순위/계/비고/청약일정등)을 통째로
  삭제했다** — 엑셀 열뿐 아니라 "수정" 탭의 관련 입력 필드
  (특별공급·1순위·2순위 당해/기타 건수, 비고)와 `doAdd()`/`saveEdit()`의
  관련 읽기/쓰기 로직도 함께 제거했다. 이 기능만 검증하던
  `e2e_v65_subscription_fields_test.js`는 이제 존재하지 않는 기능을
  테스트하므로 삭제했다.
- **중도금 이자 계산 표를 메인 표(1~19열=A~S) 바로 옆 V(금리)~AC(입주)
  위치로 옮겼다** — "메인 표 끝+3열부터 이자표 시작" 규칙(17차에서 확립,
  28+3=31 → 이번엔 19+3=22)을 그대로 적용했다. T·U(20·21열)는 참고 파일과
  동일하게 의도적인 빈 칸으로 남긴다. 이자표는 메인 표와 서식이 다른 독립된
  칸이라 파악해, 메인 헤더의 medium 강조나 파란 배경(FH)을 주지 않고 순수
  thin 상자 테두리 + 무배경으로 통일했다(이전엔 메인 헤더 서식을 그대로
  물려받아 상단 medium/파란 배경이 섞여 있었다).
- **회차별 일수(이자표 3행)가 하드코딩 숫자 대신 실시간 수식
  (`=$입주일칸$행-회차날짜칸$행`)이 됐다** — 참고 파일이 그렇게 돼 있었고,
  입주일/회차일이 나중에 수정돼도 이자 계산이 자동으로 따라가게 하는 효과도
  있다.
- **날짜 서식을 `yyyy.mm.dd`에서 `mm-dd-yy`로 바꿨다** — 참고 파일의 실제
  numFmt을 그대로 따랐다.
- **표 전체를 촘촘한 격자(모든 칸 thin 상자 테두리)로, A열 왼쪽/S열
  오른쪽에만 medium 외곽선으로 바꿨다.** 금액 열(I~S, 9~19열)은 데이터/요약
  행에서 오른쪽 정렬, A~H(1~8열)는 가운데 정렬 — 단, **헤더 행의 라벨
  자체는 금액 열이라도 가운데 정렬을 유지한다**(참고 파일에서 확인, 실제
  구현 중 실수로 헤더까지 오른쪽 정렬했다가 검증 과정에서 발견해 수정).
- **A~E(전용면적~약식표기) 세로 병합 테두리 규칙을 다시 잡았다** — 타입의
  첫 행에만 위쪽 thin이 붙고, 아래쪽은 어떤 행에도 붙지 않는다(다음
  행/소계의 위쪽 선이 경계 역할을 대신한다). A열은 오른쪽 테두리 없이
  왼쪽만 medium.
- **F(동호별) 열은 타입 전체가 아니라 "연속된 같은 동" 구간별로 병합**한다
  — 위쪽 thin은 타입의 맨 첫 행에만(동이 중간에 바뀌어도 새로 붙지 않음),
  아래쪽 thin은 각 동 구간의 마지막 행에만 붙는다.
- **소계/평형합계/합계 세 요약 행의 수식 패턴이 서로 다르다는 걸 참고
  파일에서 역산해 그대로 반영했다:**
  - 소계: `I`(분양가)=SUMPRODUCT 가중평균, `K`/`N`(확장비/옵션비)=타입 첫
    행 참조(상수), `J/L/M/O/P/R/S`는 소계 행 자신의 `I/K/N/Q`를
    `C{첫행}`으로 나눠 파생 — C열 자체는 빈 칸(18차에서 채웠던 것을 더
    구체적인 참고 파일 근거로 되돌림).
  - 평형합계: `C`는 `D`(명목 공급세대수) 가중평균, `D`는 자기 `H` 자기참조,
    `I~S` 전부 `H` 가중평균(소계처럼 파생 계산하는 지름길이 없음).
  - 합계: `C`는 `H` 가중평균, `D`는 각 타입 첫 행의 `D` 합, `I/K/N/Q`는
    `H` 가중평균, `J/L/M/O/P/R/S`는 소계와 같은 방식으로 파생.
  - (이전 코드는 평형합계/합계의 `D`열 패턴이 서로 뒤바뀌어 있었다 —
    참고 파일 대조로 발견해 맞바꿨다.)
- **같은 평형(약식표기 앞자리 숫자)이 한 타입뿐이면 "OO합계" 행을 만들지
  않는다** — 참고 파일에 그런 사례가 없었다.
- **단지명 제목 배경색을 18차의 종류별 분리(오피스텔=자주, 아파트=주황)에서
  다시 단일 복숭아색(`FFECC3B2`)으로 되돌렸다** — 새 참고 파일은 5개 단지
  전부(아파트/오피스텔 구분 없이) 같은 색이었다. 더 구체적이고 최신인 참고
  파일을 우선했다.
- 컬럼 A 너비를 13.25로, 헤더 행 높이를 47.25로(회차별 일수 행은 34.9)
  참고 파일 기준에 맞췄다.

**의도적으로 참고 파일과 다르게 남겨둔 부분(버그 아님):**
- 참고 파일은 모든 행(소계/평형합계/합계 포함)의 중도금 이자를 "분양가의
  10%"로 가정한 수식(`=(($I8*0.1)*$금리)*(일수/365)`)을 쓰지만, 이는 15차
  때 이미 실제 회차별 납부액(40%+10% 등 실제 비율)과 다르다는 걸 확인하고
  고친 부분이라 되돌리지 않았다. 대신 정확한 행별 이자 합계를
  `SUMPRODUCT`/가중평균으로 요약 행에 반영한다.
- 참고 파일 시트 맨 위 1~2행에 있던 "당사매입부지" 배너(시트 전체에 한 번만
  있는 골드색 제목)는 단지 블록 단위 요소가 아니라 그대로 재현하지 않았다.

**검증**: 참고 파일의 실제 데이터(의정부역 센트럴 아이파크 74A/84A/84B)를
Playwright `page.evaluate()`로 앱의 `units` 배열에 직접 주입해(소스 PDF가
없으므로 파서를 우회) `doExport()`를 그대로 실행한 뒤, 결과를 다시
openpyxl로 참고 파일과 셀 단위 대조했다. 그 과정에서 위에 나열한 격차들을
순서대로 발견하고 고쳤다.

`e2e_v65_excel_restructure_test.js`를 22차 구조 기준으로 전면 재작성(19/19
통과, 실제 PDF 픽스처 `songdo_g53_officetel.pdf` 사용)했고, 기존 테스트들도
바뀐 열 위치/서식에 맞춰 갱신했다:
- `e2e_v65_meta_interest_fix_test.js`: 이자표 열 참조를 AE~AH→V~Y로, 일수
  체크를 하드코딩 숫자 비교에서 실시간 수식 문자열 비교로 변경.
- `e2e_v65_summary_interest_fix_test.js`: 이자표 첫 회차 열 참조를 AF→W로
  변경.
- `e2e_v65_excel_style_test.js`: 청약현황 블록(T~AC)·구 이자표 위치(AE~AL)
  관련 체크(구 S11~S15, S20)는 새 restructure 테스트와 중복돼 제거하고,
  단지명 제목 배경색을 종류 구분 없는 단일 색 검증으로, 헤더 행 높이/A열
  너비 기대값을 새 수치로, 소계 C열 검증은 A~D 병합 때문에 ExcelJS
  재읽기로는 슬레이브 셀이 마스터 값을 반사해 직접 검증이 불가능해(기존에
  확인된 병합 읽기 함정과 동일) 설명 주석만 남기고 제거했다.
- `e2e_v65_subscription_fields_test.js`: 삭제(더 이상 존재하지 않는 기능).

`npm test`(파서 단위 테스트 전체)와 `npm run test:e2e`(전체 22개 e2e
스위트) 모두 정상 통과를 확인했다.

**남은 과제**: 사용자가 이번 요청에서 함께 제기한 "PDF는 인식되는데 내용이
타입별 분양가/확장비 등으로 전환이 안 된다"는 문제는 "일반적인 현상"이라고만
설명됐고 재현 가능한 구체적 파일은 확인하지 못했다. 이번 라운드는 엑셀
내보내기 재작성에 집중했고, 이 문제는 재현 가능한 문서가 확보되는 대로 별도로
조사해야 한다.

### 25차: 단지별 요약본(AF~AK) 신규 추가

사용자가 "내보내기 예시인데 단지별 요약본 추가하려고 하는데 AF~AK열 부분 참고해서 요소
하나하나 파악해서 그대로 넣어서 작성해줘"라며 실사용 예시 파일(메인 표와 같은 시트, 각
단지 데이터 시작행부터 AF~AK열에 붙는 타입별 요약 표가 이미 수기로 채워진 5개 단지짜리
문서)을 제공했다. openpyxl로 그 예시의 값·수식·서식을 전부 뜯어봐 반영했다.

- **위치**: 각 단지의 메인 표 데이터 시작행(제목행+5)부터 AF열에 시작한다 - 메인 표
  (A~S)·이자표(V~AC) 오른쪽으로 충분히 떨어져 있어 겹치지 않는다.
- **구성**: 1행(단지명 = 메인 표 제목 실시간 참조 + "*공급평형기준" 안내) → 2행(사용승인일
  + 총 세대수) → 헤더 2행(구분(평형)/세대수/분양가, 타입/전용(평)/공급(평)/평균/평당가) →
  타입별 요약 행들 → 맨 아래 "평균"(전체 가중평균) 행.
- **타입 묶음 기준이 메인 표의 "OO합계"(약식표기 숫자 접두부 일치)와 다르다** — 이 요약본은
  "평형대"(전용평수를 10평 단위로 내림한 값)로 묶인다. 예시 파일 5개 단지를 전부 대조해
  확인했다(예: 102와 124는 약식표기 접두부가 다르지만 둘 다 30평대라 한 그룹, 115와 126도
  마찬가지 - 반대로 121과 166은 둘 다 단독 타입이지만 서로 다른 평형대라 따로 묶임). 처음엔
  메인 표와 같은 "약식표기 접두부" 기준으로 오인할 뻔했으나, 실제 값(전용면적×0.3025)으로
  역산해 다른 기준임을 확인하고 코드로 재검증했다.
  - 평형대에 타입이 하나뿐이면: 그 타입 행 + 자기 값을 그대로 반복하는 마감행(옅은 주황)
    2행으로 마무리.
  - 둘 이상이면: 타입별 행 + 세대수(AI)로 가중평균한 마감행(옅은 주황) 1행으로 마무리.
  - 맨 아래 "평균" 행(옅은 빨강)은 항상 각 평형대의 "마감행"만 참조해 전체를 다시
    가중평균한다 - 단일/그룹 여부와 무관하게 참조 지점이 균일해지는 설계다.
- **의도적으로 예시와 다르게 반영한 부분**: 예시 파일의 "총 N 세대수"는 하드코딩 텍스트였지만,
  이 프로젝트는 값을 하드코딩하지 않고 항상 수식으로 참조해 편집에 따라 갱신되게 하는
  원칙이므로 그 단지의 합계 행(H열)을 실시간 참조하는 문자열 결합 수식으로 바꿨다. 또한
  예시의 두 번째 단지("2-2BL") 평균 행 AG/AH열이 첫 번째 단지("2-1BL")의 행 번호를 그대로
  복사해온 명백한 복사·붙여넣기 오류(같은 행의 AI/AJ/AK열은 정상)를 발견해, 정상 열과
  같은 패턴(그 단지 자신의 마감행 참조)으로 통일했다 - 오류를 그대로 베끼지 않았다.
- **서식**: 예시의 실제 테마 색을 openpyxl로 역산 - 헤더는 회색(FFD9D9D9), 마감행은

### 28차: 그룹 합계(group_key/group_label) 오버라이드 - 자동 묶음 규칙이 안 맞는 단지 대응

목동윤슬자이 오피스텔의 세부(호실/층별) 분양가를 직접 입력해준 뒤, 사용자가 "타입 별
평균 내는게 전체표랑 정리표랑 안 맞기도 하고"라며 원하는 묶음 방식을 직접 지정했다
(115A/114B/114C를 하나로, 117C-T1~120A-T3를 하나로, 198CD~203AD를 하나로). 기존 두
자동 규칙 - 메인 표 "OO합계"는 약식표기 숫자 접두부 일치, AF~AK 요약본은 전용면적
10평 단위 내림 - 둘 다 이 단지에는 안 맞았다: 6개 타입(115/114/117/118/119/120)이
전부 접두부가 달라 메인 표 규칙으로는 하나도 안 묶이고, 반대로 전용면적이 전부
34.5~36.4평이라 AF~AK 규칙으로는 원치 않는 8개 타입이 통째로 한 그룹(30평대)이 됐다.

원문 공급대상표 자체가 "1군 115A / 2군 114B / 3군 114C / 4군(117C-T1~120A-T3) / 5군
(198CD~203AD)"로 군을 나눠뒀고, 사용자가 원한 건 이 군 구분에서 1~3군을 합친 것과
같았다 - 즉 자동 규칙으로 일반화하기보다는, 문서마다 다를 수 있는 "실제 타입 유사군"을
사용자가 직접 알려주면 그대로 반영할 수 있는 탈출구가 필요했다. 타입 데이터에 선택적
`group_key`(묶음 판별 기준값)/`group_label`(합계 행 라벨, 생략 시 group_key 그대로)를
추가해, 있으면 두 표(메인 표 "OO합계" + AF~AK 요약본) 모두 이 값을 최우선으로 쓰고
없으면 기존 두 자동 규칙을 그대로 쓰도록 했다(기존 문서는 전부 이 필드가 없으므로
회귀 없음).

### 28차 후속: 그룹 오버라이드를 "수정" 탭 UI에서 직접 입력할 수 있게 확장

28차에서 만든 group_key/group_label은 Claude가 스크립트로 unit 객체에 직접 주입해야만
쓸 수 있었다. 사용자가 "해당 논리를 프로그램에도 적용해줘"라고 요청해, 사용자가 새 PDF를
올릴 때마다 매번 요청하지 않고도 앱 UI만으로 직접 쓸 수 있게 만들었다.

자동으로 일반화하는 방안(예: "-T" 접미사가 붙은 코드는 항상 별도 그룹, 두 글자 이상
접미사는 항상 별도 그룹)도 검토했지만, 기존 실사례(힐스테이트 둔산 오피스텔 - 84A~84G
안에 "84E1-T"/"84E2-T"가 섞여 있고, 전부 "84"라는 같은 숫자 접두부로 묶이는 게 이미
검증된 정답)로 확인해보니 위험했다. 그 문서에서는 "-T" 접미사가 있어도 같은 84 평형대의
변형일 뿐 별도 그룹이 아닌데, "자동으로 -T는 별도 그룹" 규칙을 적용했다면 이미 맞던 결과가
망가졌을 것이다. 즉 "묶어야 할 타입"은 문서마다 사정이 달라 코드 패턴만으로 일반화할 수
없다는 뜻이므로, 자동 규칙을 더 정교하게 만드는 대신 "수정" 탭에 타입별 **합계 그룹**
입력칸을 추가해 사용자가 직접, 그때그때 알려줄 수 있게 했다. 같은 문자열을 입력한
타입끼리 묶이고(입력값이 곧 group_key이자 라벨), 비워두면 기존 자동 규칙(숫자 접두부/
전용면적 10평 단위) 그대로다.

## 전체 프로세스 재검증에서 발견한 회귀 4건

PDF 첨부→분석→추가→요약/수정 탭→엑셀 다운로드까지 실제 브라우저로 처음부터 끝까지
다시 돌려보며 결과값을 직접 대조하는 과정에서 발견한 문제들. 전부 실사례
PDF(`fixtures/hillstate_dunsan_officetel.pdf`)로 재현·검증했다.

1. **PDF 첨부 경로에서 오픈일/입주예정일이 항상 미인식됐다.** `extractMeta`가
   공급금액/공급면적 입력란 텍스트만 검색하는데, 공고일·입주예정일 문구
   (`■ ...로 분양신고`, `■ 준공 및 입주예정일 : ...`)는 그 두 섹션 밖에 있는 경우가
   많다. 지금까지의 e2e 테스트가 이 결함을 못 잡은 이유: 손으로 붙여넣은 실사례
   텍스트는 사람이 보통 그 문구까지 함께 넉넉하게 복사해서 우연히 통과했지만, PDF
   자동 추출은 섹션 경계를 정확히 지키므로 항상 실패했다. PDF 첨부 시점에 추출한
   원문 전체를 `lastPdfFullText`로 보관해뒀다가 메타 추출에 함께 사용하도록
   고쳤다(직접 붙여넣기 경로는 이 값이 없어 기존 동작 그대로 유지).
2. **중도금 회차가 6회가 아니면 이자가 통째로 0으로 계산됐다.** `doAdd()`가
   `mid_dates.length===6`이 아니면 전부 버렸는데, 실사례 중 6회 미만(2회/4회/5회)인
   문서가 드물지 않다(이 문서는 2회). 있는 회차만큼만 반영하도록 완화했다.
3. **중도금 이자 계산 열이 하나씩 밀려 있었다.** `56+i+1`이어야 할 계산식이
   `55+i+1`(오프셋 실수)로 되어 있어, 1차 회차가 금리(BD)를 저장하는 칸을 침범하고
   나머지 회차는 전부 한 칸씩 밀리며, 마지막 6번째 회차 칸(BJ)은 아예 쓰이지 않았다.
   같은 오프셋 실수가 있는 데이터 행/헤더 날짜 행/일수 행 세 곳 모두 `56+i+1`로
   고쳤다.
4. **중도금 이자를 "분양가의 10%"로 가정해 계산했다.** 회차마다 균등 10%인 문서만
   맞는 값이 나오고, 회차 비율이 다른 실사례(예: 이 문서의 "1차중도금40%+2차중도금10%")는
   전부 틀린 원금으로 계산됐다. 원인은 `adapter_v65.js`가 파서가 이미 정확히 추출한
   회차별 실제 금액(`row.mid_amounts`)을 기본 UI로 넘기는 과정에서 통째로 버리고
   있었기 때문 - `{dong, floor, units, price}` 4개 필드만 남기고 나머지(중도금
   회차별 금액, 계약금, 잔금 등)를 전부 잘라내는 어댑터였다. `mid_amounts`를
   보존하도록 고치고, 이자 수식이 이제 이 실제 금액을 직접 참조하도록 바꿨다.

**추가로 확인했지만 이번 라운드에서 완전히 고치지 못한 항목**: 이 문서의 옵션표는
"■ 추가선택 옵션품목 납부계좌"라는 별도 제목이 바로 뒤에 있어, 옵션 섹션이 그
유의사항 산문까지 통째로 삼켜버리는 문제가 있었다(그 산문 속 "당 현장의
84A,B,C,D,E타입 호실은..." 문장이 84A의 옵션가로 오인됨) - 이건 `splitDocumentSections`가
다음 "■"/"▣" 제목을 안전한 종료 경계로 추가해 해결했다(`findNextHeadingBoundary`,
`test_cases_l.js`). 하지만 이 문서의 옵션표 자체는 "전 타입"(전체 타입 공통 적용)
표기에 특정 타입만 제외하는 각주("84D 일부 제외", "84G 제외")가 섞인, 11개 카테고리
(현관/거실/드레스룸/붙박이장/에어컨/욕실/주방/냉장고/오븐/식기세척기 등)를 한
표에 나열하는 형식이라, `parseAmountByCodeSection`의 "코드 뒤 순수 한글 라벨은
연속 그룹으로 본다"는 연속행 인식 규칙이 각 품목의 여러 단어짜리 설명 문구에도
반응해, 이미 확정된 코드가 다음 품목 행까지 끌려가 엉뚱한 금액을 줍는 경우가
남아있다(예: 84D가 실제로는 12,400,000원인 항목이 아니라 6,820,000원인 다른
항목의 값을 가져옴). 이 패턴과 고양창릉 실사례(`test_cases_h.js` H06, "기본형"/
"마이너스옵션" 두 가격이 같은 코드에 이어지는 정당한 사례)가 토큰 단위 규칙으로는
**서로 구분이 안 되는 것**을 직접 확인했다(연속 그룹 생성을 "직전 그룹 금액 미확정
시에만 허용"으로 제한해봤더니 H06이 깨졌다) - 안전한 일반화에는 줄바꿈 경계를
보존한 행 단위 인식이 필요해 이번 라운드에서는 보류했다. 이런 다항목 카탈로그형
옵션표를 쓰는 문서는 옵션가를 직접 확인해야 한다.

## 설계 원칙: 헤더 특수케이스 나열 대신 데이터의 내적 일관성으로 자가검증

실제 문서를 하나씩 검증할 때마다 "이번엔 이렇게 깨져 있네"라는 새 조합이 계속
나오는 문제가 있었다(헤더 라벨/코드 형식/구분자마다 정규식을 하나씩 추가하는 방식은
조합이 사실상 무한하다). 그래서 핵심 로직을 **헤더 텍스트를 읽어 구조를 "추측"하는
대신, 데이터 자체에 존재하는 산술적 일관성으로 구조를 "검증"하는 방식**으로 전환했다:

- **가격 컬럼 구조** (`detectPriceColumnStructure`): "대지비+건축비+(부가세)=합계"가
  성립하는 지점을 찾아 오프셋과 행당 컬럼 개수를 알아낸다. 후보 행 하나가 아니라
  발견되는 모든 행에서 같은 구조에 투표하게 해 다수결로 확정하므로, 헤더에
  대지비/건축비/부가세/계약시/입주시 같은 키워드가 **전혀 없어도** 동작한다
  (`test_cases_g.js` G01: 임의 라벨 "A B C D E F1..G"로만 된 헤더에서도 정확히 구조를
  알아냄). 중도금 날짜도 "중도금N차" 라벨 없이 나열된 연속 날짜 구간으로 찾는다
  (`detectMidDatesGeneric`).
- **공급면적 전용/공급 판별** (`findAreaTriple`): 코드 숫자가 면적을 반영한다는
  가정(예: "84A"→84㎡) 대신, "전용면적+공용면적=소계(공급면적)" 관계를 면적값들
  사이에서 직접 찾는다. 계약면적=소계+기타공용처럼 여러 단계로 누적돼도 가장 작은
  합계(가장 안쪽 단계)를 우선한다. 코드가 면적과 무관한 임의 표기(오피스텔 호실번호,
  라인번호 등)에도 코드 힌트 없이 정확히 동작한다(`test_cases_g.js` G02, G03).
  3개 미만의 면적값만 있어 산술 검증이 불가능할 때만 코드 숫자 접두부 근접도
  휴리스티크로 폴백한다.
- **표 오염 교정**은 특정 키워드가 아니라 형태적 일관성으로 판단한다: 콤마 자릿수가
  맞는 숫자 뒤에 여분의 숫자가 곧바로 붙으면 행 경계로 간주(`fixGluedNumbers`,
  가격/면적/발코니·옵션 섹션 공통 적용), 발코니·옵션의 "코드 없이 이어지는 설명행"도
  특정 단어 목록을 나열하는 대신 "순수 한글 라벨이면 무엇이든"(기본형/마이너스옵션/
  전실/앞으로 나올 어떤 새 단어든) 인식한다(`CONTINUATION_RE` + `isLabelToken`).
- **세대수 컬럼이 아예 없는 가격표**도 지원한다: 층구분 뒤에 세대수 대신 서브옵션
  라벨(기본형/마이너스옵션 등)만 있거나 그마저 없이 곧장 금액이 오는 경우까지
  처리하며(`readMoneyRun`), 라벨 쪽 서브옵션 행은 자신의 층 토큰 없이 이어져도
  직전 층을 이어받는다. 층구분 자체가 "5층~ 최상층"처럼 공백으로 두 토큰에
  걸쳐도 하나로 합친다(`skipFloorPrefix`).
- **대지비/건축비 분리 표기가 아예 없는 가격표**("주택가격" 한 컬럼뿐)도 지원한다.
  이 경우 산술로 검증할 수 없으므로 여러 행에서 같은 컬럼 개수가 일관되게 반복될
  때만 근거로 삼는다. 중도금 블록의 위치도 "값이 서로 거의 같게 반복되는 구간"으로
  찾아(`findMidBlockStart`) 잔금 뒤에 융자금처럼 추가 컬럼이 더 있어도 정확하다.
- **긴 그룹코드 하나에 서로 다른 짧은형 하위타입이 여러 개 딸린 공급대상표**
  ("059.0000A" 안에 59AL/59A/59AH가 각기 다른 면적·세대수로 존재)도 지원한다.
  짧은형 코드를 우선 경계로 삼아(긴 코드는 짧은형이 전혀 없을 때만 폴백) 하위타입이
  뭉개지지 않게 한다.
- **"소계" 중간값이 아예 인쇄되지 않는 공급면적표**(전용/공용/기타공용/주차장면적
  4개 값을 모두 더해야만 계약면적이 되고, 그 사이 어떤 3항 조합도 서로 합이 맞지
  않는 경우)도 `findAreaTriple`이 3개 미만 매칭 시 폴백하는 코드숫자-근접도
  휴리스틱으로 여전히 전용면적/계약면적을 정확히 골라낸다. 타입 코드의 영문 접미사가
  2글자를 넘는 경우("65GTB", "66GTA"처럼 3글자)도 `SHORT_CODE_RE`가 코드 경계로
  인식하도록 접미사 길이 제한을 2글자→3글자로 넓혔다(고치기 전에는 이런 코드가
  아예 경계로 잡히지 않아 인접 타입의 면적값을 덮어쓰는 회귀가 있었다).
- **계약금이 "계약 시"/"계약 후 N일 이내" 두 컬럼으로 쪼개져 있고 중도금이 5회
  균등분할인 가격표** — `readMoneyRun`/`buildPriceColumnMap`이 이미 down 컬럼 여러 개를
  합산하도록 일반화돼 있어 별도 수정 없이 정확히 동작함을 실사례로 확인했다.
- **타입 코드에 하이픈+영문 접미사가 붙는 경우**("84E1-T", "84E2-T"처럼 짧은형 코드
  뒤에 "-T" 등이 더 붙음): `SHORT_CODE_RE`에 `(?:-[A-Za-z]{1,3})?` 선택 그룹을 추가해
  일반화했다(고치기 전에는 코드 경계로 아예 인식되지 않아 해당 타입 전체가 누락됐다).
- **중도금이 회차별로 불균등 분할된 가격표**("1차중도금 40%+2차중도금 10%"처럼 두
  중도금 회차의 금액 규모가 다름): 대지비/건축비 분리 표기가 없어 "값이 서로 거의
  같게 반복되는 구간"으로 중도금 블록을 찾는 `findMidBlockStart`가, 절대 편차 합으로
  비교하면 절대값이 작은 계약금(5%+5%) 구간을 상대적으로 "더 고르다"고 오판해 중도금
  구간 대신 골라버리는 문제가 있었다. 구간 평균 대비 상대 편차로 비교하도록 일반화해
  해결했다(고치기 전에는 계약금/중도금/잔금이 전부 뒤바뀌어 나왔다).
- **콤마 뒤 공백으로 두 토큰에 걸쳐 쪼개지는 층 목록**("11, 15층"이 토큰화 시 "11,"과
  "15층"으로 분리됨): 층 토큰 인식(`isFloorToken`)이 끝에 콤마/물결/붙임표만 남은
  토큰("11,")을 층 표기로 인정하지 않아, 뒤 토큰("15층")만 남고 앞부분이 통째로
  유실되는 문제가 있었다. 끝에 붙은 구분자로 끝나는 토큰을 층 목록의 계속되는 부분으로
  인식하도록 `isFloorToken`/`skipFloorPrefix`를 일반화했다.
- **pdf.js 재배치로 공급면적표 본문 전체가 공급금액 섹션 앞부분에 섞여 들어가는 PDF**
  (더샵 송도그란테르 G5-3블록 오피스텔 실제 PDF): 사용자가 "PDF 첨부로 공급면적을
  인식 못한다"고 제보해 발견. `splitDocumentSections`가 "▣ 공급대상" 제목 기준
  1차 분리만 하면 area 섹션에 안내문만 남았는데, 각 표 바로 앞에 항상 붙는
  `(단위 : ㎡...)`/`(단위 : 원...)` 표기를 2차 경계로 삼아 재분리하는
  `repairMisplacedAreaTable`을 추가해 해결했다(복구한 조각이 실제로 유효한 면적
  행을 만들어낼 때만 채택 - "실패하면 두 섹션을 합쳐서 재시도"하는, 앞서 폐기했던
  폴백과는 다른 안전한 메커니즘).
- **옵션 섹션 제목에 접두어가 붙는 경우**("▣ 별도계약 - 추가 선택품목"): 기존 OPTION
  앵커가 이 형식을 인식하지 못해, 문서 뒤쪽의 무관한 "▣ 추가 선택품목 납부계좌 및
  납부방법"(계좌 안내일 뿐 옵션표가 아님) 제목을 대신 골라버리는 문제가 있었다.
  해당 형식을 앵커 후보에 추가해 해결.

`test_cases_g.js`(4건)와 `test_cases_h.js`(6건)는 지금까지 확인된 어떤 실제 사례에도
없던(g) 또는 세 번째 실사례에서 발견된(h) 조합이다 — 특정 사례에 맞춘 패치가 아니라
메커니즘 자체가 일반화됐는지 검증하기 위한 것이다. 실제 확인된 12개 단지 분양공고
사례(의정부역 센트럴 아이파크, 영통역 우미린, 김포 풍무 레이크에듀시티, 번영로
롯데캐슬, 더폴 우정, 더샵 송도그란테르(아파트), 힐스테이트 안양 펠루스, 더폴
울산신정, 더샵 송도그란테르 G5-3블록(오피스텔), 고양창릉 S-4블록(공공분양),
시화MTV 푸르지오 디오션 오피스텔, 힐스테이트 둔산 오피스텔)도 `test_cases_d.js`~

브라우저 UI까지 검증).

### 여전히 남아있는 제한사항

- **코드가 숫자로 시작하지 않는 형식** (예: "T05"처럼 문자가 먼저 오는 코드): 코드
  인식 정규식이 "숫자로 시작"을 전제하므로 지원하지 않는다(지금까지 확인된 실제
  사례는 전부 숫자로 시작해 우선순위가 낮음).
- **코드 없이 라인번호만 있는 동/라인 표기** (예: "1", "3"만 있고 "동"/"호"/"라인" 접미사가
  없는 경우): 층 번호와 구분할 근거가 없어 지원하지 않음. "라인" 접미사가 있는 경우만 인식.
- **접미사 없는 순수 소수 코드** (예: "059.9700" 단독, 문자 없음): 순수 면적값과 형태가
  동일해 구분 불가능하므로 지원하지 않음(실사례에서도 확인되지 않은 형식). 순수 숫자 코드는
  정수형("76", "105")만 지원.
- 공공분양처럼 가격표의 행이 "세대수"가 아니라 "층×옵션 조합"만 나타내는 문서에서는,
  요약 화면의 "표기N/합산M" 경고가 실제 오류가 아니라 이 문서 특성상 자연스럽게
  발생할 수 있다(공급대상표의 총세대수와 가격표의 행 개수가 서로 다른 것을 세는
  값이기 때문). 오류로 오인하지 말고 참고 정보로만 볼 것.
- 공급대상표에 전용/공용면적 외에 특별공급 세부내역처럼 아주 많은 숫자 열이 있는
  초대형 표(예: 공공분양 "공급규모" 요약표)는 총공급세대수 판별이 부정확할 수 있다
  (첫 정수 채택 규칙이 "1층세대수" 같은 다른 소수 항목을 잘못 고를 위험). 이런 경우
  결과 탭의 "데이터 수정"에서 직접 확인·수정하는 것을 권장한다.
- 가격 섹션에서 데이터 기반 컬럼 구조 감지가 실패하면(층구분+세대수+금액런 형태의 행을
  전혀 찾지 못하는 경우 등) "대지비"부터 헤더 라벨을 순서대로 읽는 레거시 방식으로
  폴백하며, 이 경우 날짜 컬럼이 최소 1개는 인식돼야 하고 계약금은 "%" 비율 표기가 있을
  때만 정확히 인식된다.
- 근본적으로 규칙/정규식 기반 접근은 "표가 텍스트로 한 번 풀어지면 원래의 2차원 구조를
  완벽하게 복원하는 것은 원리적으로 불가능"하다는 한계가 있다. 데이터 내적 일관성
  검증으로 무작정 특수케이스를 나열하는 것보다는 훨씬 일반화됐지만, 검증할 산술
  관계 자체가 없는(혹은 텍스트가 너무 많이 손상된) 문서는 여전히 실패할 수 있다.
  더 근본적인 범용성이 필요하면 LLM 기반 표 해석을 보조 경로로 추가하는 방안을 검토할 것.
