# QA 피드백 (Agent D → Agent A)

## 1차 실행 결과: 16/18 (test_cases.js)

### 실패 케이스: A7 (메타정보: 공고일 파싱)
- 재현: `extractMeta('입주자 모집공고일: 2024.03.10 입주예정월: 2026년 5월')`
- 결과: `open_date`의 일(day)이 10이 아닌 1로 파싱됨
- 원인: 공고일 추출 정규식의 마지막 캡처 그룹이 `\d{1,2}?`(레이지 반복자)로 작성되어 있어
  "10"에서 "1"만 매칭되고 "0"이 버려짐. `?`를 그룹 전체의 선택적 존재가 아니라
  반복자에 붙여 의미가 달라진 전형적인 정규식 실수.
- 수정: `\d{1,2}?` → `\d{1,2}` (레이지 수량자 제거)

### 실패 케이스: B11 (계약금 정액/비율 동시 지원)
- 재현: `parsePriceSection('...  120  10,000,000  350,000,000', ['084.9750A'])`
- 결과: `down_payment`가 10,000,000이 아닌 120으로 계산됨
- 원인: 금액 토큰 판정 기준이 `길이 >= 3`이어서 세대수 컬럼의 "120"이
  금액 토큰으로 오인되어 최솟값(계약금 후보) 계산을 오염시킴
- 수정: 금액 토큰 최소 길이를 4자리로 상향 (`tk.length >= 4`).
  세대수는 통상 1~3자리, 분양대금 관련 금액은 4자리 이상이라는 도메인 지식 반영.

## 구조적 개선: 코드 인식 방식 변경

`parsePriceSection` / `parseBalconySection` / `parseOptionSection`이 코드를
정규식(`영문+숫자` 패턴)으로만 추측하던 방식은 "순수 숫자.소수 코드"(예: `059.9700`,
문자 접미사 없음) 형식에서 실패할 수 있음이 C04, C21 케이스 설계 중 발견됨.

- 수정: `codes` 인자가 주어지면 라인 토큰 중 `codes` 배열과 **정확히 일치하는 토큰**을
  최우선으로 코드로 채택하고, 실패 시에만 정규식 휴리스틱으로 폴백하도록 변경.
- 효과: 임의의 코드 표기(아파트형 관리번호, 오피스�텔 호형, 숫자.소수만 있는 코드 등)에
  견고해짐. `parseAreaSection`이 먼저 추출한 codes를 이후 단계에 전달하는 설계
  의도(계약서에 명시된 시그니처)와도 부합.

## 2차 피드백: 실제 확인된 8개 단지 사례 반영 (test_cases_d.js)

사용자가 실제 분양공고 8종(의정부역 센트럴 아이파크, 영통역 우미린, 김포 풍무 레이크에듀시티,
번영로 롯데캐슬, 더폴 우정, 더샵 송도그란테르, 힐스테이트 안양 펠루스, 더폴 울산신정)에서
확인한 패턴을 반영하는 과정에서 다음 버그를 발견·수정함.

### 코드 판별 우선순위 오류
- `SHORT_CODE_RE`(84A 등) 우선순위는 맞았으나, 그 다음 순위였던 "면적값에 인접한 순수정수"
  휴리스틱이 세대수 컬럼("120")을 코드로 오인하는 사고가 발생(A1 회귀).
  → 순서를 짧은형 → 긴 소수형(LONG_CODE_RE) → 순수정수(최후 수단)로 재배치하고,
    순수정수 후보를 "첫 면적값의 바로 앞/뒤 칸"으로만 제한.
- `LONG_CODE_RE`의 문자 접미사를 선택(`{0,2}`)으로 두었더니 순수 면적값("59.9700")까지
  코드로 오인(A3/C03 회귀). 실제 사례에서 접미사 없는 장문형 코드는 확인되지 않아
  문자 접미사를 필수(`{1,2}`)로 변경.
- "101A"(오피스텔 호실번호)처럼 코드 숫자가 면적과 무관한 경우, 코드-면적 근접도 휴리스틱이
  엉뚱한 값을 전용면적으로 채택(A2 회귀). 근접도가 코드값 대비 50% 이상 벗어나면
  신뢰하지 않고 오름차순 최솟값으로 폴백하도록 안전장치 추가.

### 발코니/에어컨(묶음형) 처리 시 mega-line 분리 로직 충돌
- 표 전체가 개행 없이 한 줄로 직렬화된 경우를 처리하려 만든 `expandMegaLines`가
  "여러 코드가 한 줄을 공유하는 묶음형" 옵션 행(예: "76, 84A, 84B, 84C, 84D  4대  2,200,000")을
  코드 개수만큼 강제로 쪼개버려 마지막 코드만 금액을 받는 문제 발생(D28).
  → 발코니/옵션 섹션에는 mega-line 분리를 적용하지 않도록 변경(가격 섹션에만 유지).

### 신규 지원 항목
- 합계 오프셋은 "합계/소계/계" 라벨과 무관하게 부가세 유무로만 판단됨을 재확인(변경 없음, 회귀 테스트만 추가).
- 층구분: 공백 포함 범위("4층~6층"), 혼합 나열("6,8~9"), 공백 포함 이상표기("41층 이상"),
  괄호+이상 라벨("고층(16층이상)") 지원.
- 날짜: 2자리 연도(24.09.25), 말미 마침표(2026.10.15.), 슬래시 구분(2026/10/06),
  상대일자("계약 후 30일이내" 등, `parsePriceSection`의 3번째 인자 baseDate로 절대일자 환산) 지원.
- 계약금: 층마다 다른 비율형, "5%+5%" 분납 비율 합산 지원.
- 옵션가: N안형/N대형/기본·전실형("최소 채택" = 코드별 등장 금액 중 최솟값), 묶음형(코드 여러개가
  금액 하나를 공유) 지원.
- PDF 복사 오염: "잔금대지비" 같은 키워드 붙음 교정(`despaceKeywords`), 코드 내부 공백("84 A") 병합,
  표 전체가 한 줄로 직렬화된 경우 codes를 앵커로 행 분리(`expandMegaLines`, 가격 섹션 한정).

## 3차 피드백: 근본 설계 결함 - "헤더를 무시하고 앵커를 추측" (사용자 실제 원문 제보)

사용자가 실제 "더폴 울산신정" 공고문 원문(가격표/공급대상표/발코니/에어컨)을 그대로
붙여넣었을 때 **아무것도 인식하지 못함**을 확인. 근본 원인 두 가지:

1. **가격 섹션이 헤더의 명시적 컬럼 순서를 무시하고 있었음.** 실제 헤더는
   "대지비 건축비 합계 계약시 24.09.25 25.02.25 ... 입주시"처럼 각 컬럼이 무엇인지
   순서대로 명시하는데, 기존 파서는 이를 버리고 금액 크기(최댓값=공급금액, 최솟값=계약금)로
   추측하고 있었다. 실제 데이터에서는 계약금(32,610,000)이 세대수(1) 다음으로 작은 값이
   아니라 우연히 작아 보였을 뿐이고, 중도금 날짜는 "중도금1차" 같은 텍스트 라벨이 아니라
   헤더의 날짜 컬럼 자체("24.09.25")로만 표기되어 기존 정규식(`중도금\s*\d\s*차`)이 전혀
   매칭되지 않았다.
   → `buildPriceColumnMap` + `scanPriceRowsWithMap`을 신설해 헤더에서 대지비/건축비/
     (부가세)/합계/계약시/날짜×N/입주시 순서를 실제로 읽어 컬럼맵을 만들고, 그 맵 그대로
     데이터 컬럼을 배정하도록 재설계(레거시 추측 방식은 컬럼맵을 못 찾을 때만 폴백).
2. **표 전체가 개행 없이 한 줄로 이어지고, 코드/동호수가 매 행마다 반복되지 않음.**
   기존 파서는 줄 단위로 행을 인식했는데, 실제 문서는 "84A 101동1호 3층 1 ... 4층~6층 3 ...
   102동1호 3층 1 ... 84B 101동 2·3호 3층 2 ..."처럼 코드/동호수가 새로 나올 때만 갱신되고
   그 뒤 여러 층구분 행이 이어지는 구조라, 애초에 "한 줄=한 행" 가정이 성립하지 않았다.
   → 코드/동호수를 상태로 유지하며 토큰 스트림을 순회하는 상태기계로 재작성. 공급대상표도
     동일하게 표 전체가 한 줄로 이어지는 경우가 있어(특별공급 세부내역까지 포함된 복잡한
     헤더), 코드 토큰을 경계로 세그먼트를 분리하는 방식으로 `parseAreaSection`도 재작성.
     세대수는 "면적값 이후 첫 정수"(총공급세대수, 이후 특별공급 세부내역이 이어짐) 규칙으로
     교정(기존엔 마지막 정수를 취해 특별공급 세부 항목을 오인).
3. **발코니/에어컨(코드당 여러 금액이 한 줄에 나열)에서 최솟값 채택 규칙이 잘못 일반화됨.**
   "84A 23,000,000(공급금액) 2,300,000(계약금) 20,700,000(잔금)"처럼 한 코드에 딸린
   여러 금액 중 최솟값을 집으면 계약금(2,300,000)을 공급금액으로 오인한다. N안/N대/기본·
   전실형(최소 채택)과 공존시키기 위해 "코드(그룹)당 처음 등장하는 금액만 후보로 취하고,
   그 그룹이 바뀔 때(새 코드 또는 안/대/기본/전실/전체 등 연속 트리거)만 새 후보를 추가해
   후보들 중 최솟값을 취하는" 방식으로 재설계.

## 4차: 사용자 제공 UI(app_v65_source.html)로 프론트엔드 교체 (Agent B 영역)

사용자가 별도로 만들어 둔(또는 이전 세션에서 산출된) 프론트엔드 파일을 제공하며
"인터페이스·레이아웃이 더 낫다"고 하여 이를 기본 UI로 채택. 그 파일 자체의 파서(v4,
앵커/정규식 추측 방식)는 이번 대화에서 문제가 됐던 것과 동일한 구조적 한계를 가지고
있어(계약금 앵커 추측, "중도금N차" 텍스트 라벨 의존 등) 교체 대상으로 삼고, UI·상태관리·
엑셀 빌더(37열 서식 포함)·JSON 저장 로직은 그대로 유지.

- `adapter_v65.js` 신설: 이 UI가 기대하는 호출 규약(parsePriceSection이 code→rows 맵을
  반환, extractMeta가 날짜를 문자열로 반환)으로 parser.js를 감싸는 얇은 어댑터.
  parseAreaSection/parseBalconySection/parseOptionSection은 형태가 이미 동일해 그대로 재사용.
- `extractMeta` 보강: 이 UI의 원 파서가 지원하던 "공고일" 키워드 없이
  "...날짜(...)로 입주자모집공고 승인" 형태, "입주예정월/일" 없이 "입주시기"만 표기된
  경우를 parser.js에도 흡수(E07, E08 테스트로 고정) — 두 프론트엔드가 하나의 파서를
  공유하도록 유지하기 위함.
- `build_v65.js` 신설: app_v65_source.html의 옛 파서 구간만 정확히 잘라내고
  parser.js + adapter_v65.js로 교체해 dist/분양가정리.html(기본 산출물)을 생성.
  기존 build.js는 레거시 UI 전용으로 남기고 출력 경로를 dist/legacy_분양가정리.html로 분리
  (두 빌드가 같은 파일을 덮어쓰지 않도록).
- e2e_v65_test.js로 실제 원문 데이터를 이 UI에 입력해 분석→추가→사이드바→요약/수정/원본
  탭→엑셀·JSON 다운로드까지 검증. 오픈일(2024.02.28), 입주(2027년2월), 중도금 6/6,
  84A/84B 세대수(56/112), 확장비(23,000,000), 옵션(4,070,000) 모두 정확히 일치.

## 5차: 두 번째 실사례(더샵 송도그란테르 G5-3블록 오피스텔)에서 새로운 실패 유형 발견

사용자가 v6.5 기반 UI에 이 문서를 넣었더니 "⚠ 표기2/합산0"(가격행 0건)로 여전히
실패함을 확인. 이전 사례(울산신정)와는 다른 세 가지 새로운 문제였음:

1. **공급대상표 세그먼트 경계의 "-2 토큰 lookback"이 이전 행 꼬리를 침범.** 같은
   전용/공급면적을 공유하는 타입이 연달아 나오고(84OA, 84OB가 값이 동일) 행 사이에
   구분자가 거의 없는 표에서, 각 코드 세그먼트를 "코드 위치 - 2"부터 시작하다 보니
   이전 타입의 꼬리 float 2개가 섞여 들어와 "면적값 앞/뒤 정수" 판별 로직이 세대수
   정수를 float 클러스터 사이에 낀 것으로 오인해 놓쳐버림(84OB~84OG 전부 유실,
   마지막 84OH는 총계행 "계 24"의 24를 세대수로 오인).
   → 세그먼트를 "코드 자신부터 다음 경계 직전까지"(꼬리 침범 없음)로 우선 시도하고,
     면적먼저형처럼 코드 앞에 데이터가 있어 실패할 때만 "-2" 확장을 재시도하는 방식으로
     변경. 총계행 컷오프도 "합계"/"합 계" 외에 "계 24"처럼 "합" 없이 "계"+숫자만 오는
     경우(마지막 코드 경계 이후에 한해)까지 인식하도록 확장.
2. **가격 헤더가 계약금 2회분납(1차/2차) + 부가세 구조인데다, 회차 라벨 자체가
   깨져 있음**("1차 2차 1차(10%) 2차(10%) 4차(10%) 4차(10%) 5차(10%) 6차(10%)" -
   3차가 빠지고 4차가 중복). 라벨을 순서대로 읽는 기존 방식으로는 이런 헤더를
   신뢰성 있게 컬럼맵으로 바꿀 수 없음.
   → `detectPriceColumnStructure` 신설: 헤더 라벨을 아예 읽지 않고, 데이터 행 자체에서
     "대지비+건축비+(부가세)=합계"가 성립하는 지점을 찾아 오프셋과 행당 컬럼 개수를
     스스로 알아낸다. 중도금 날짜도 "중도금N차" 라벨에 의존하지 않고 라벨 없이 나열된
     연속 날짜 구간을 찾는 `detectMidDatesGeneric`으로 보완. 계약금이 여러 컬럼(1차+2차)
     이면 합산해 하나의 down_payment로 반영하도록 `scanPriceRowsWithMap`도 수정.
     기존 헤더-라벨 순차읽기 방식은 이 데이터기반 감지가 실패할 때만 쓰는 폴백으로 격하.
3. **표가 행 경계에서 개행은 물론 공백도 없이 그대로 붙어 복사됨** ("189,000,0009층",
   "194,100,00084OB" - 이전 행의 마지막 금액과 다음 행의 층/코드가 공백 없이 이어짐).
   → `fixGluedNumbers` 신설: 제대로 된 3자리 콤마 구간(예: "189,000,000") 뒤에 콤마 없이
     여분의 숫자가 곧바로 붙으면 그 지점에 공백을 삽입해 분리.
4. 공고일 텍스트에 날짜 내부에 공백이 섞인 경우("2026. 5. 13.")도 미인식되어
   `extractMeta`의 승인/신고 날짜 정규식에 공백 허용을 추가.

test_cases_f.js(6건)로 회귀 고정, e2e_v65_songdo_test.js로 v6.5 UI에서도 8개 타입
전부(84OA~84OH, 세대수 2/2/2/2/4/4/4/4) 및 중도금 6/6 인식 확인.

## 6차: 아키텍처 재검토 - "예시마다 그 예시만 고치는" 패턴을 근본적으로 줄이기

사용자가 "새 문서를 넣을 때마다 그 문서에 해당하는 부분만 수정돼서 작동한다"는
구조적 문제를 지적. 실제로 지금까지 5차에 걸친 수정이 전부 "헤더 키워드/코드 형식
특수케이스를 하나씩 추가"하는 방식이었고, 이는 조합이 사실상 무한해 반복될 수밖에
없는 패턴이었음. 핵심 설계를 "헤더 텍스트로 구조를 추측" → "데이터 자체의 산술
일관성으로 구조를 검증"하는 방식으로 전환:

1. **detectPriceColumnStructure 다수결 투표화**: 후보 행 하나의 우연한 산술 일치로
   확정하지 않고, 발견되는 모든 행에서 같은 (오프셋, 컬럼개수) 구조에 투표하게 해
   다수결로 확정. 잘못된 우연 일치에 더 강건해짐.
2. **findAreaTriple 신설(가장 큰 변화)**: 공급면적 전용/공급 판별을 "코드 숫자가
   면적을 반영한다"는 가정(예: "84A"→84㎡ 근접도)에서 "전용면적+공용면적=소계"라는
   면적값들 사이의 산술 관계를 직접 찾는 방식으로 전환. 코드가 면적과 무관한 임의
   표기(오피스텔 호실번호, 라인번호 등)에도 코드 힌트 없이 정확히 동작 — 이게 바로
   "이번 예시에만 맞는 코드 힌트 로직"이었던 부분을 없앤 것.
3. **fixGluedNumbers를 가격 섹션 전용에서 면적/발코니·옵션 섹션까지 공통 적용**:
   특정 섹션에만 있던 오염 교정을 형태적 일관성(콤마 자릿수) 기준으로 전체에 적용.
4. **CONTINUATION_RE 일반화**: "안/대/기본/전실/전체/추가" 같은 특정 단어 목록 대신
   "숫자+한글단어" 일반 패턴으로 확장.

test_cases_g.js(4건) 신설 - 지금까지 확인된 어떤 실제 사례에도 없던, 의도적으로
새로 지어낸 조합(헤더 키워드 전혀 없는 가격표, 면적과 무관한 코드, 3단계 누적
면적체인, 처음 보는 연속행 라벨)으로 메커니즘 자체의 일반화를 검증. 특정 사례가
아니라 "새로운 조합에도 이 원리가 통하는가"를 증명하는 것이 목적.

**정직하게 밝히는 근본적 한계**: 규칙/산술검증 기반 접근은 표가 텍스트로 풀어지며
2차원 구조가 사라진 것을 "완벽하게" 복원할 수는 없다. 검증할 산술 관계 자체가
없거나 텍스트가 심하게 손상된 문서는 여전히 실패할 수 있음. 진짜 범용성을
원한다면 LLM 기반 표 해석을 보조 경로로 추가하는 것을 사용자에게 제안(API 키
입력 필요, 네트워크/비용 발생하는 아키텍처 변경이라 별도 논의 필요).

## 7차: 세 번째 실사례(고양창릉 S-4블록 공공분양)에서 새로운 실패 패턴 발견

6차에서 "예시마다 그 예시만 고치는" 패턴을 근본적으로 줄이겠다고 한 직후, 세 번째
실사례(공공분양주택, 지금까지와 형식이 확연히 다름)에서 다시 실패를 확인. 원인 4가지:

1. **긴 그룹코드 하나에 서로 다른 짧은형 하위타입이 1:1이 아니라 여러 개 딸림.**
   "059.0000A" 안에 59AL/59A/59AH(각기 면적·세대수 다름)가 있는데, 기존 로직은
   "긴 소수형 코드가 있으면 우선 경계로 삼는다"였어서 세 하위타입이 한 세그먼트로
   뭉개짐(59AL 하나만 남고 나머지 유실, 그마저 총계행 숫자를 세대수로 오인).
   → 경계 우선순위를 뒤집어 짧은형 코드를 항상 우선(관리번호형은 짧은형이 긴 코드와
     1:1 대응이라 문제 없음), 짧은형이 전혀 없을 때만 긴 코드로 폴백.
2. **가격표에 대지비/건축비 분리 표기가 아예 없음**("주택가격" 한 컬럼뿐, 잔금 뒤에
   융자금이라는 추가 컬럼까지 있음). detectPriceColumnStructure는 오프셋 3/4만
   검증 가능해 이 구조를 아예 못 찾았음.
   → 오프셋 1(검증 불가, 총액이 첫 컬럼) 폴백을 추가하되 여러 행에서 같은 컬럼
     개수가 일관될 때만 신뢰하도록 안전장치. mid 블록 위치도 "값이 서로 거의 같게
     반복되는 구간"으로 직접 찾도록 바꿔(`findMidBlockStart`) down/mid/balance
     경계를 위치가 아니라 값의 성질로 정확히 구분(잔금+융자금처럼 mid 뒤에 여러
     컬럼이 있어도 정확).
3. **세대수 컬럼 자체가 없고, 같은 층에서 "기본형"/"마이너스옵션" 두 가격이 나열됨**
   (마이너스옵션 쪽은 자신의 층 토큰 없이 이어짐). 기존 행 인식은 "층+세대수+금액"
   패턴만 지원해 이 구조를 아예 못 찾음.
   → 세대수(선택)/서브옵션 라벨(선택)/곧장 금액 세 가지를 모두 지원하도록 재작성
     (`readMoneyRun`), 라벨만 있는 연속행은 직전 층을 이어받도록 상태 추가.
     이 과정에서 "콤마 구분 금액(60,857)이 층 목록(5,7,9)과 형태가 겹쳐 층으로
     오인되는" 회귀 버그를 발견해 금액 형태는 층에서 먼저 배제하도록 수정.
4. **발코니 섹션의 연속행 라벨이 하드코딩 목록에 없는 새 단어("마이너스옵션")라
   전혀 인식되지 못함.** 6차에서 "숫자+한글단어"만 일반화했지 순수 한글 단어
   전체는 놓치고 있었음 — 정확히 "새 단어가 나올 때마다 목록에 추가"하던 옛 패턴이
   남아있던 지점. 특정 단어 나열을 완전히 버리고 "순수 한글 라벨이면 무엇이든"
   (`isLabelToken`) 연속행 트리거로 인정하도록 일반화.

test_cases_h.js(6건) 신설, e2e_v65_goyang_test.js로 v6.5 UI에서도 59AL/59A/59AH
하위타입 분리, 세대수 없는 기본형/마이너스옵션 10개 행, "5층~ 최상층" 층구분까지
확인. 참고: 이 문서 특성상 가격표 행(층×옵션 조합)과 공급대상표 세대수가 서로 다른
값을 세므로 "표기N/합산M" 경고가 뜨는 것은 정상이며 오류가 아님(README에 명시).

**발견 1 — 영문 접미사 3글자 코드가 아예 경계로 인식되지 않음.** 시화MTV 푸르지오
디오션의 타입 코드 중 "65GTB", "65GTC", "66GTA"는 영문 접미사가 3글자인데,
`SHORT_CODE_RE`가 `[A-Za-z]{1,2}`로 최대 2글자까지만 허용하고 있어서 이 세 코드는
아예 세그먼트 경계로 잡히지 않았다. 그 결과 해당 타입들이 통째로 유실되거나(3개 타입
실종), 인접 타입의 세그먼트가 다음 타입의 면적값까지 삼켜버려 엉뚱한 전용/계약면적이
나오는 오염이 발생했다(64TA2, 65TC2가 대표적으로 틀렸음). → `SHORT_CODE_RE`의 영문
접미사 허용 길이를 `{1,2}`에서 `{1,3}`으로 넓혀 해결. 특정 코드 하나를 화이트리스트에
추가하는 방식이 아니라 "영문 접미사 길이" 자체의 일반화이므로 향후 4글자 이상 접미사가
나오면 같은 방식으로 재검토하면 된다.

**발견 2 (버그 아님, 검증됨) — "소계" 중간값이 아예 없는 4항 합산형 공급면적표도
기존 폴백으로 정확히 처리됨.** 이 문서의 공급면적표는 전용면적/공용면적/기타공용면적/
주차장면적 네 값을 모두 더해야 계약면적이 되고, 그 사이 어떤 두 값을 더해도 세 번째
값과 맞아떨어지는 3항 관계가 전혀 없다(기존 `findAreaTriple`이 기대하는 "전용+공용=소계"
형태가 아예 인쇄돼 있지 않음). 코드를 고치기 전에 먼저 확인해보니, `findAreaTriple`이
유효한 3항 관계를 찾지 못하면 이미 있던 "코드숫자 접두부 근접도" 폴백이 자동으로
발동해 전용면적/계약면적을 정확히 골라내고 있었다 — 별도 수정 불필요. (발견 1의
코드 경계 버그만 고치면 이 폴백 경로 자체는 이미 일반화돼 있었다는 뜻.)

**발견 3 (버그 아님, 검증됨) — 계약금 2분할("계약 시 5%"+"계약 후 1개월 이내 5%") +
중도금 5회 균등분할 가격표도 기존 로직으로 정확히 처리됨.** `buildPriceColumnMap`이
이미 down 컬럼 여러 개를 합산하도록 일반화돼 있어서, 이 새로운 조합(계약금 2회+중도금
5회+잔금 1회)도 코드 수정 없이 계약금 10%/중도금 각 회차 10%/잔금 40%가 전부 정확히
분리됐다.

test_cases_i.js(5건) 신설, e2e_v65_sihwamtv_test.js로 v6.5 UI에서도 16개 타입
전부(3글자 접미사 타입 포함) 인식 및 53TA/119P 분양가가 요약 탭에 정확히 렌더링되는지

## 9차: 프로그램 방향 전환 - 텍스트 붙여넣기 → PDF 첨부 자동인식

사용자가 "분양광고 PDF 전체를 첨부하면 알아서 인식하는 방향이 더 효율적이지 않겠냐"고
제안했고, 검토 결과 실제로 확인한 모든 PDF가 스캔 이미지가 아니라 **텍스트 레이어가
있는 PDF**였으므로(OCR/LLM 없이도) client-side `pdf.js`만으로 충분하다고 판단해 방향을
전환했다.

**구현**
1. `pdfjs-dist`(legacy 빌드, UMD)를 `vendor/pdfjs.min.js` + `vendor/pdfjs.worker.min.js`로
   받아 `app_v65_source.html`에 xlsx와 같은 방식으로 직접 인라인. 워커는 `<script
   type="text/plain">`로 텍스트만 담아두고 런타임에 Blob URL로 변환해 `workerSrc`로
   지정 — 외부 파일 참조 없이 "오프라인 단일 HTML" 원칙 유지.
2. 텍스트 추출 시 **아이템을 그대로 이어붙이고 `hasEOL`에서만 개행을 삽입**하는 방식을
   채택. 처음엔 아이템 사이에 무조건 공백을 넣었더니 "구분"이 "구 분"처럼 매 음절마다
   공백이 끼는 문제가 발생했는데, pdf.js가 이미 필요한 공백/줄바꿈을 자체 아이템으로
   정확히 내려주고 있어서 그 위에 추가로 손대지 않는 것만으로 실제 문서 4건 모두에서
   표 구조가 거의 원문 그대로 재구성됨을 확인했다.
3. `parser.js`에 `splitDocumentSections(fullText)` 신설: "■"/"▣" 불릿으로 시작하는
   섹션 제목("공급대상 및 공급규모", "공급금액 및 납부일정", "발코니 확장", "추가선택
   옵션품목" 등)을 앵커로 4개 섹션 경계를 찾는다. 디스클레이머 불릿("⦁"/"•")과 섞이지
   않아 오탐이 없음을 실제 문서로 확인했다. **문서 전체를 그대로 파서에 넣는 방식은
   시도했다가 폐기**했다 — 실험해보니 무관한 페이지의 우연한 숫자 조합이 가짜 타입으로
   인식되는 사례("84G ... 0.2 ... 1.2"가 유효한 삼항관계로 오인됨)를 실제로 발견해서,
   반드시 섹션을 먼저 좁혀야 안전하다고 판단했다.
4. UI에 "📄 PDF 첨부" 버튼 추가(`handlePdfUpload`) — 첨부 즉시 4개 입력란을 자동
   채우고, 못 찾은 섹션은 비워둬서 사용자가 직접 채우게 하며, 공급면적을 찾았는데도
   0건 파싱되면 별도 경고를 띄운다.

**실사례로 발견한 잔여 한계 (버그 수정이 아니라 설계 결정으로 기록)**
- 더샵 송도그란테르 G5-3 PDF를 실제로 넣어보니, pdf.js의 텍스트 재구성 순서가
  시각적 순서와 100% 일치하지 않아 공급면적표의 "(단위: 호실, ㎡)" 표기가 공급금액표
  헤더 뒤로 밀려나 두 표가 한 섹션으로 합쳐지는 현상을 발견했다. 이 경우 "실패하면
  두 섹션을 합쳐서 재시도"하는 폴백을 시도해봤으나, 합쳐서 재시도하면 대부분 타입은
  살아나도 마지막 타입 하나의 세대수가 총계행 숫자로 둔갑하는(4 → 24) 조용한 오염이
  실제로 발생함을 확인해서 **이 폴백은 채택하지 않기로 했다**. 조용히 틀린 값을 주는
  것보다 명시적으로 "표를 못 찾았다"고 실패하는 편이 금액을 다루는 도구에서 더
  안전하다는 이 프로젝트의 기존 원칙과 일치한다.
- 한 PDF에 서로 다른 두 분양공고가 함께 들어있으면(이번 4건 중 최소 1건이 그랬음)
  섹션 앵커는 문서상 첫 번째 것만 채택한다.
- 스캔 이미지 PDF(텍스트 레이어 없음)는 지원하지 않는다(OCR/비전 LLM 필요, 현재

## 10차: 사용자가 직접 업로드한 실제 PDF 4건 중 다섯 번째 실사례(힐스테이트 둔산 오피스텔)에서 새로운 회귀 발견

9차에서 PDF 첨부 기능을 다 붙인 뒤, 사용자가 처음 업로드한 4건 중 아직 실제 파싱을

`fixtures/hillstate_dunsan_officetel.pdf`)를 실제로 넣어보고 발견한 회귀 3건.

1. **하이픈+영문 접미사 타입코드 미인식**: "84E1-T", "84E2-T"처럼 짧은형 코드 뒤에
   하이픈으로 접미사가 더 붙는 형식이 있었는데, `SHORT_CODE_RE`가 하이픈을 전혀
   지원하지 않아 이 코드들이 아예 경계로 인식되지 않았다(해당 타입 전체 누락).

2. **중도금 불균등 분할 시 `findMidBlockStart` 오판**: 이 문서의 중도금은
   "1차(40%)+2차(10%)"로 두 회차 금액이 서로 다른데, 대지비/건축비 분리 표기가 없어
   "값이 서로 거의 같게 반복되는 구간"을 찾는 `findMidBlockStart`가 절대 편차 합으로
   비교하다 보니, 절대값 자체가 작은 계약금(5%+5%, 수백만~수천만원대) 구간을
   중도금(수억원대) 구간보다 "더 고르다"고 오판해 계약금 자리에 배정해버렸다.
   그 결과 계약금/중도금/잔금이 전부 뒤바뀌어 나왔다(예: 84A 4~5층 잔금이 실제
   431,550,000원인데 911,050,000원으로 나오는 식). 절대 편차 대신 **구간 평균 대비
   상대 편차**로 비교하도록 일반화해 해결.
3. **콤마+공백으로 쪼개지는 층 목록 유실**: "11, 15층"처럼 콤마 뒤에 공백이 있는 층
   목록이 토큰화 과정에서 "11,"과 "15층" 두 토큰으로 분리되는데, `isFloorToken`이
   끝에 콤마만 남은 토큰("11,")을 층 표기로 인정하지 않아 뒤 토큰만 남고("15층")
   앞부분이 조용히 유실됐다. 끝에 구분자(콤마/물결/붙임표)로 끝나는 토큰을 층
   목록의 계속되는 부분으로 인식하도록 `isFloorToken`/`skipFloorPrefix`를 일반화해
   해결(3개 이상 이어지는 목록에도 대응).

세 건 모두 "이 문서 하나만 고치는" 패치가 아니라 정규식/판정 로직 자체를 일반화하는

## 11차: 사용자가 "PDF 첨부해도 공급면적을 인식 못한다"고 제보(더샵 송도그란테르 G5-3블록 오피스텔)

사용자가 "이 PDF는 지금 프로그램으로 공급면적을 인식 못한다"며 실제 PDF를 첨부해줘서

**원인**: pdf.js가 이 문서를 텍스트로 재구성하는 순서가 시각적 순서와 어긋나 있었다.
"▣ 공급대상" 제목 바로 뒤에는 안내문 4줄만 남고, 실제 공급면적표 본문(8개 타입 전부)이

결과, area 섹션은 안내문뿐이라 파싱 결과가 0건, price 섹션 앞부분에는 공급면적표가
그대로 섞여 있는 상태였다(README에 6차부터 "여전히 남아있는 한계"로만 기록해두고
실제 자동 복구는 시도하지 않았던 바로 그 패턴).

**수정**: `parser.js`에 `repairMisplacedAreaTable(area, price)`을 추가했다. area 섹션이
실제로 빈 것으로 확인될 때만(`parseAreaSection(area).length === 0`) 시도하며, 두 표가
항상 자기 표 바로 앞에 두는 고유 단위 표기 — 면적표는 `(단위 : ㎡...)`, 가격표는
`(단위 : 원...)` — 를 2차 경계로 찾아 price 섹션 앞부분에서 실제 면적표만 정확히 잘라
area 섹션에 붙이고, price 섹션은 그 뒤(진짜 가격표 시작 지점)부터 다시 시작하게 했다.
복구한 조각이 실제로 유효한 면적 행을 만들어낼 때만(`parseAreaSection(recovered).length > 0`)
채택하고, 그렇지 않으면 조용히 포기해 기존 동작(안내문만 남은 area 섹션, 명시적 실패)으로
되돌아간다 — 9차에서 폐기했던 "실패하면 두 섹션을 합쳐서 통째로 재시도"하는 폴백과는
분명히 다른 메커니즘이다. 그 폴백은 구분자 없이 area+price 전체를 한꺼번에
`parseAreaSection`에 밀어 넣어 무관한 숫자가 섞여 들어가는 조용한 오염(세대수 4 → 24)을
일으켰지만, 이번 복구는 각 표 고유의 단위 표기로 경계를 정확히 잘라내고 결과를 검증한

아니라 계좌 안내일 뿐)을 대신 골라버렸다. `SECTION_ANCHORS.option`에 해당 형식을
추가해 해결했다.

## 12차: 새 실사례를 못 찾음 - 이번 세션 네트워크 정책으로 웹 원문 접근 자체가 막힘 (코드 변경 없음)

새 단지 분양공고 원문을 찾아 파서를 검증하려 했으나, **이번 세션에서는 WebFetch/curl로
외부 웹의 실제 문서 원문에 전혀 접근할 수 없었다.** 이전 라운드들과 달리 이번 세션의
아웃바운드 네트워크 정책이 매우 좁은 허용목록(주로 github.com/gitlab.com/bitbucket.org/
npm·pypi류 개발 도구 도메인)만 허용하고 나머지는 프록시 단계에서 전부 403으로 차단하는
것을 다음과 같이 직접 확인했다:

- `curl`로 25개 이상의 서로 다른 도메인을 시도(분양공고 PDF를 호스팅하는
  `files-scs.pstatic.net`, `prugio.com`, `hillstate-hec.co.kr`, `image.r114.co.kr`,
  `d2o59jgeq8ig2.cloudfront.net` 등은 물론, 정부/공공기관 사이트인
  `apply.lh.or.kr`/`www.molit.go.kr`/`www.data.go.kr`, 블로그 플랫폼인
  `blog.naver.com`/`tistory.com`, 심지어 부동산과 무관한 `wikipedia.org`,
  `example.com`, `httpbin.org`까지) — **전부 프록시 단계에서 `CONNECT tunnel failed,
  response 403`으로 거부**됐다(`curl -sS "$HTTPS_PROXY/__agentproxy/status"`의
  `recentRelayFailures`에 "gateway answered 403 to CONNECT (policy denial)"로 기록됨).
  반면 `github.com`/`api.github.com`/`raw.githubusercontent.com`/`gitlab.com`/
  `bitbucket.org`/`s3.amazonaws.com`(베어 호스트)은 정상 연결됐다 — 즉 이번 세션은
  기본거부(deny-by-default) 정책으로 개발 도구 도메인 소수만 허용하고 있었다.
- `WebFetch` 도구도 같은 차단을 그대로 겪었다(`en.wikipedia.org`조차 403). 반면
  `github.com` 같은 허용 도메인은 정상 fetch됐다 — WebFetch가 같은 아웃바운드
  프록시 정책을 공유한다는 뜻.
- `WebSearch`만 유일하게 동작했지만(허용목록 밖의 사이트여도 검색 결과 스니펫과
  요약을 반환), **동일한 질의를 반복하면 서로 다른, 원문과 대조 불가능한 숫자를
  내놓는다는 것도 직접 확인했다**: 화성 남양뉴타운 우미린 에듀하이 84A 타입에 대해
  첫 질의에서는 "대지비 97,302,000원 + 건축비 361,098,000원 = 458,400,000원"이라는
  산술적으로 앞뒤가 맞는 답을 내놓았는데(마치 실제 표처럼 보임), 곧바로 거의 동일한
  질의를 다시 하자 이번엔 세부 비용 분할 정보 자체가 없다며 완전히 다른 답을 내놓았다.
  즉 WebSearch의 요약 답변은 "그럴듯하게 산술이 맞는 것"조차 재현되지 않는 것으로
  보아 소형 모델이 만들어낸 추정치일 가능성이 높고, **원문 그대로를 옮겨적었다는
  근거가 되지 못한다.**

이 프로젝트의 핵심 원칙(3번 - 실사례만 사용, 조작 금지)에 따라, 검증 불가능한

않기로 했다. 대신 이번 라운드는 **새 테스트/코드 변경 없이** 다음만 수행했다:
1. 기존 회귀 스위트 전체 재실행 — 변동 없이 전부 통과(아래 최종 결과 참고).
2. 이 네트워크 제약 사실을 여기에 정직하게 기록.

이 제약은 파서 자체의 한계가 아니라 **이번 세션의 아웃바운드 네트워크 정책**이므로
README.md의 "여전히 남아있는 제한사항"(파서 설계 한계 전용 섹션)에는 넣지 않았다.

## 13차: 사용자가 제공한 실제 엑셀 예시와 대조해 엑셀 내보내기 스타일/구조 개선

사용자가 "엑셀 내보내기가 요구사항을 반영하지 못한다"며 원하는 결과물 예시 엑셀(부동산
매입 검토용, 여러 단지의 아파트/오피스텔 분양가를 정리한 실사용 파일)을 첨부했다. Python
`openpyxl`로 셀 값·수식·폰트·배경색·테두리·병합범위를 전부 뜯어서 현재 `buildBlock`
(`app_v65_source.html`)과 대조했다.

**근본 원인(가장 중요한 발견)**: 격차를 하나씩 고치기 전에, 다운로드된 실제 xlsx의
`styles.xml`을 열어보니 코드에서 지정한 폰트/배경색/테두리가 **단 하나도 저장되지
않고 있었다**(기본 Calibri 폰트 하나뿐). 원인은 벤더링된 SheetJS(`xlsx` 패키지)가
**커뮤니티(무료) 에디션**이라는 것 — 셀 스타일 **쓰기**는 SheetJS Pro 버전 전용
기능이라, 커뮤니티판은 스타일 객체를 지정해도 에러 없이 조용히 버린다. 같은 이유로
행 높이(`rh`)도 계산은 되지만 실제로 적용하는 코드가 없어 버려지고 있었다. 즉
"셀 색상/폰트/크기가 반영 안 된다"는 사용자 지적은 코드 로직 문제가 아니라 **애초에
쓸 수 없는 라이브러리를 쓰고 있었던 것**이 원인이었다.

**조치**: 스타일 쓰기를 지원하는 오픈소스 **ExcelJS**(MIT)로 엑셀 생성 부분만
교체했다. `vendor/exceljs.min.js`(브라우저 번들, 925KB)를 xlsx.js/pdf.js와 동일한
방식으로 `app_v65_source.html`에 인라인하고, `doExport()`/`buildBlock()`을 ExcelJS
API(`ws.getCell(r,c)`, `cell.font`/`cell.fill`/`cell.border`/`cell.numFmt`,
`wb.xlsx.writeBuffer()` + Blob 다운로드)로 재작성했다. 기존 SheetJS 전용 헬퍼
(`mkC`, `adr`/`colL` 좌표 문자열 변환)는 ExcelJS가 `getCell(row, col)` 숫자 접근을
직접 지원해 불필요해져 제거했다.

**구조적 격차 4가지**도 함께 고쳤다(라이브러리 교체와 무관하게 실제로 있던 버그/누락):
1. **아파트/오피스텔 평당가 산정 기준 미분리**: 아파트는 공급면적 기준(공급평수),
   오피스텔은 전용면적 기준(전용평수)이어야 하는데 `kind`와 무관하게 항상 공급면적
   기준이었다. `isOfficetel` 분기로 C열 계산식(`=B*0.3025` ↔ `=A*0.3025`)과 헤더
   라벨을 모두 갈랐다.
2. **같은 평형대 그룹 합계 행("84합계" 등) 부재**: 타입 소계 → 바로 전체 합계로
   직행해, 84A+84B처럼 같은 평형 여러 타입을 한눈에 비교할 방법이 없었다. 약식표기
   코드의 숫자 접두부로 그룹을 묶어, 타입 소계와 전체 합계 사이에 그룹 가중평균
   행(초록 배경)을 추가했다. 그룹 행은 참고용 중간 집계일 뿐이고, 전체 합계는
   참고 엑셀과 동일하게 타입별 소계에서 직접 집계하도록 유지했다(그룹 행을 거치지
   않음 - 계산 경로를 바꾸면 반올림 오차가 누적될 수 있어 원본 산식을 그대로
   따랐다).
3. **테두리 스타일 완전 부재**: `mkC`에 border 파라미터 자체가 없었다. 헤더/타입
   경계/소계/그룹합계/전체합계 각각에 참고 엑셀과 동일한 두께 위계(얇음/굵음)를
   부여했다.
4. **헤더 배경색 불일치**: 회색(D9D9D9) → 참고 엑셀의 연한 파랑(테마 Accent1 80%
   틴트, 계산값 DEEBF7)으로 교체.

**이번 라운드에서 하지 않은 것(명시적으로 보류, 사용자와 합의)**:
- 청약 경쟁률(특별공급/1순위/2순위 접수건수)·계약 진행 현황(일자별 계약 건수/잔여/
  분양률)·청약일정 텍스트 컬럼은 헤더만 있고 값이 없다. 이 데이터는 분양공고
  원문에는 없고 분양 진행 중 실시간으로 갱신되는 정보라, 지금 UI/파서가 애초에
  입력받지 않는다. 엑셀 코드만 고쳐서는 채울 수 없어 억지로 빈 값을 만들어 넣지
  않기로 했다(실사례 조작 금지 원칙과 같은 결). UI 입력 필드 추가는 사용자가 명시적으로
  "추후 별도 라운드"로 미루기로 확인했다.
- PDF 표를 pdf.js의 "읽기 순서 텍스트" 대신 x/y 좌표 기반으로 기하학적으로
  재구성하는 개선(사용자 제안, 11차의 재배치 버그와 같은 근본 원인)도 사용자와
  합의해 별도 라운드로 분리했다.

**테스트**: `e2e_v65_excel_style_test.js` 신설 — Playwright로 실제 UI에서 아파트/
오피스텔 단지를 각각 추가해 엑셀을 다운로드한 뒤, Node의 ExcelJS로 다시 읽어
1) 제목/헤더/소계/그룹합계/전체합계의 폰트·배경색·테두리가 `styles.xml`에 실제

3) 행 높이·열 너비가 적용됐는지까지 10건 검증(값이 아니라 스타일 자체를 검증한다는

## 14차: 13차에서 보류한 두 항목 - ① PDF 좌표기반 표 인식 실험(채택 보류), ② 청약/계약 현황 입력 필드 추가

### ① PDF 좌표(x/y) 기반 표 인식 - 프로토타입 검증 후 채택하지 않기로 결정

pdf.js의 `getTextContent()`가 반환하는 아이템은 실제로 페이지 콘텐츠 스트림 순서일
뿐 시각적 순서가 아님을 직접 확인했다(더샵 송도그란테르 G5-3 문서 3페이지에서,
페이지 하단 푸터 텍스트 "- 3 -"가 아이템 배열의 맨 처음에 나오고, 실제 상단 본문은
한참 뒤에 나옴 - `item.transform[5]`로 y좌표를 직접 찍어서 확인). 이를 근거로
"읽기 순서로 이어붙이기" 대신 y좌표로 줄을 클러스터링하고 그 안에서 x좌표로
정렬하는 재구성 함수를 프로토타입으로 만들어 실사례 PDF 3건(sihwa_mtv,
hillstate_dunsan, songdo_g53) 전부에 실제로 돌려봤다.

**결과**: 더샵 송도그란테르 G5-3의 원래 문제(제목/표 재배치)는 실제로 해결됐다 -
"▣ 공급대상" 바로 뒤에 8개 타입 전부가 정상 순서로 나왔다(`repairMisplacedAreaTable`
없이도). 하지만 **같은 문서의 가격표에서 새로운 회귀가 발생**했다: "84OA 2"처럼
2개 층 행에 걸친 세로 병합 셀의 코드 라벨이, 병합 범위의 세로 중앙 y좌표에
배치돼 있어서 순수 y좌표 정렬 시 자신이 속한 두 층 행(5층/9층) "사이"에 끼어
들어가 버렸다. 코드 캐리포워드 파싱은 코드가 층 행보다 먼저 나온다고 가정하므로
이 순서가 깨지면 가격 행 인식이 틀어진다(16개 예상 행 중 15개만 인식, 특정 행이
아예 안 잡힘). 나머지 두 실사례(시화MTV, 힐스테이트 둔산)에서도 각각 다른 지점
(특정 가격 행 유실, "11, 15층" 콤마 목록 유실)에서 같은 유형의 회귀가 나타나
**3건 전부에서 새로운 실패가 발생**했다.

**판단**: 이건 "재배치" 버그 하나를 고치는 대신 "세로 병합 셀" 버그를 새로
만들어내는 트레이드오프였다. 세로 병합 셀을 올바르게 처리하려면 단순 정렬이
아니라 열(column) 단위로 먼저 클러스터링한 뒤 각 셀의 세로 범위(row span)를
추정하는, 훨씬 큰 표 재구성 알고리즘이 필요하다. 지금까지 "재배치" 버그를
실제로 겪은 문서는 1건뿐이고 이미 `repairMisplacedAreaTable`(단위표기 2차 경계
복구, 결과 검증 후에만 채택)로 안전하게 해결돼 있으므로, 검증되지 않은 더 큰
변경으로 3건의 회귀를 만드는 대신 **채택하지 않기로 결정**했다 — "실사례로

### ② 청약 접수건수/계약 진행 현황 - 수정 탭에 입력 필드 추가

적용했다.

### ① PDF 첨부 경로에서 오픈일/입주예정일이 항상 미인식

분석 칩에 "오픈일 미인식"이 뜨는 것을 보고 재현. `doParse()`가
`extractMeta(f.taPrice + '\n' + f.taArea)`로 공급금액/공급면적 입력란 텍스트만
검색하는데, 공고일·입주예정일 문구(`■ ...로 분양신고`, `■ 준공 및 입주예정일 : ...`)는
`splitDocumentSections`가 잘라내는 4개 섹션 밖에 있는 경우가 흔하다. 지금까지의
e2e 테스트가 이 결함을 못 잡은 이유를 찾아보니: `test_cases_e.js`의 AREA_TEXT를
보면 실제로 "■ 입주시기 : 2027년 02월 예정..." 문구가 AREA_TEXT 안에 그대로
포함돼 있었다 - 사람이 손으로 붙여넣을 때는 표 주변 문맥까지 넉넉하게 복사해서
우연히 통과했던 것이고, PDF 자동 추출처럼 섹션 경계를 정확히 지키면 항상 실패하는
구조적 결함이었다.

수정: PDF 첨부 시점에 추출한 원문 전체를 `lastPdfFullText`라는 모듈 변수에 보관해뒀다가,
메타 추출 시 `(lastPdfFullText ? lastPdfFullText + '\n' : '') + f.taPrice + '\n' + f.taArea`로
함께 검색하도록 고쳤다. 직접 붙여넣기 경로는 이 값이 null이라 기존 동작과 완전히
동일하다(회귀 없음). `clearForm()`에서 초기화해 다음 단지 입력 시 이전 PDF의
원문이 새어 들어가지 않게 했다.

### ② 중도금 회차가 6회 미만이면 이자가 통째로 0

분석 칩에 "중도금 2/6"이 뜬 것을 보고, 이 문서(실제로 중도금이 2회뿐)의 엑셀
이자 컬럼을 열어보니 전부 0이었다. `doAdd()`가
`mid_dates: midDates.length===6 ? ... : null`로 정확히 6개가 아니면 통째로 버리고
있었다. `hasMidDates`가 false가 되면 `buildBlock`이 무이자 단지와 똑같이 취급해
전 회차 이자를 0으로 채운다. 실사례 중 6회 미만(2회/4회/5회)인 문서가 드물지
않으므로(이 세션에서 확인된 실사례만도 2회/5회 등 다양함), `midDates.length > 0`이면
있는 만큼만 반영하도록 완화했다.

### ③ 중도금 이자 계산 열이 하나씩 밀려 있었음(사전 존재하던 오프셋 버그)

②를 고치고 다시 확인하는 과정에서 발견. 헤더 행의 회차별 날짜 쓰기, 일수 계산
행, 본문의 이자 수식 행 세 곳 모두 `sc(55+i+1, ...)`로 회차 인덱스(i=0~5)를 열
번호로 변환하는데, i=0일 때 `55+0+1=56`은 금리(BD)를 저장하는 바로 그 열이다.
실제로는 `56+i+1`(i=0 → 57=BE)이어야 회차별 날짜/이자 계산이 "BE~BJ" 6개 열에
정확히 들어간다. 이 오프셋 실수 때문에:
- 1차 회차 데이터가 금리 열과 같은 열 번호에 쓰임(다행히 헤더 행(6행)과 본문 행(8행
  이후)은 행이 달라 실제 값 훼손은 없었지만, 본문 행에서 1차 회차 수식이 BD열에
  쓰이며 SUM 범위(BE:BJ)에서 빠짐).
- 나머지 회차가 전부 한 칸씩 밀려 써짐.
- 마지막 6번째 회차 몫은 항상 BJ가 아니라 BI에 쓰이고, BJ는 영영 비어 있음.
- `SUM(BE:BJ)`로 합계를 냈으므로, 그 결과 **1차 회차 이자가 총합에서 누락**되고
  있었다(회귀 전부터 있던 문제로 추정 - 이번에 실제 총액을 손으로 검산하다가 발견).

세 곳 모두 `56+i+1`로 수정.

### ④ 중도금 이자를 항상 "분양가의 10%"로 가정 - 회차 비율이 다른 문서에서 원금이 틀림

③을 고친 뒤 실제 수식을 열어보니 `=(($I8*0.1)*$BD$6)*(BE$7/365)`처럼 원금을
`분양가 × 10%`로 고정 가정하고 있었다. 6회 균등 10%씩인 문서에는 맞는 값이지만,
이 실사례처럼 "1차중도금40%+2차중도금10%"로 불균등 분할된 문서는 전부 틀린
원금으로 계산된다. 원인을 추적해보니 `parser.js`는 이미 회차별 실제 금액을
`row.mid_amounts`로 정확히 추출하고 있었는데(9~11차에서 이미 검증된 기능),
`adapter_v65.js`가 `parsePriceSection` 결과를 기본 UI가 기대하는 형태로 재포장하며
`{dong, floor, units, price}` 4개 필드만 남기고 `mid_amounts`(및 `down_payment`,
`balance` 등)를 전부 잘라내고 있었다. `mid_amounts`만 보존하도록 어댑터를 고치고,
이자 수식이 `row.mid_amounts[i]`를 직접 참조하도록 바꿨다(참고 엑셀도 같은
"금액×금리×일수/365" 형태였지만, 원금 자체가 항상 10%라는 가정은 참고 엑셀이
우연히 6회 균등분할 문서였기 때문에 드러나지 않았던 것으로 보인다).

### 추가로 발견했지만 이번엔 완전히 고치지 못한 것: 옵션 섹션의 "다음 대분류 제목 없음" 케이스

같은 문서에서 84A의 옵션가가 "80,007원"이라는 말도 안 되는 값으로 나오는 것을
발견했다. 원인 추적 결과 `splitDocumentSections`가 옵션 섹션을 "다음 대분류
제목"(`청약신청 자격 및 공급일정`)까지 잘라내는데, 이 문서는 그 문구가 전혀
등장하지 않아 옵션 섹션이 표 본문 뒤에 이어지는 "■ 추가선택 옵션품목 납부계좌"는
물론 그 뒤 몇 페이지에 걸친 유의사항 산문까지 통째로 삼켜버렸다. 그 산문 속에
"당 현장의 84A,B,C,D,E타입 호실은 관련 소방안전 기준에 따라..."라는 문장이 있었고,
`parseAmountByCodeSection`의 코드 토큰 스캔이 이를 진짜 가격 행으로 오인해 근처의
아무 숫자나 84A의 옵션가로 집어왔다.

**수정한 부분**: "■"/"▣"는 실제 표 항목 각주(Ÿ/⦁/•)와 달리 예외 없이 새 대분류
제목에만 쓰인다는, 이 프로젝트가 처음부터 써온 원칙을 옵션/발코니 섹션의 "종료"
경계에도 적용했다 - 자기 자신의 제목 다음에 나오는 첫 "■"/"▣"(이 경우 "추가선택
옵션품목 납부계좌")를 안전한 종료 경계로 추가(`findNextHeadingBoundary`). 이걸로
84A는 더 이상 엉뚱한 값을 받지 않는다(`test_cases_l.js`).

**수정하지 못한 부분**: 옵션 섹션이 이제 정확히 표 본문만 남았는데도, 84D는 여전히
틀린 값(12,400,000원이어야 할 것이 6,820,000원)을 받는다. 이 문서의 옵션표는
"전 타입"(전체 공통) 표기에 "84D 일부 제외"/"84G 제외" 같은 각주가 섞인, 11개
카테고리를 나열하는 카탈로그형 구조라, `parseAmountByCodeSection`의 "코드 뒤에
오는 순수 한글 단어는 같은 코드의 연속 그룹으로 본다"는 규칙이 각 품목의 여러
단어짜리 설명 문구("드레스룸", "컬렉션", "일반", "PET", "도어"...)에도 계속
반응해, 이미 확정된 코드가 완전히 다른 다음 품목 행까지 끌려가 버린다.

이걸 고쳐보려고 "직전 그룹의 금액이 아직 미확정일 때만 연속 그룹 생성을 허용"하는
제약을 추가해봤는데, 전체 회귀 스위트를 돌려보니 `test_cases_h.js`의 H06
(고양창릉 실사례, "기본형"/"마이너스옵션" 두 가격이 정당하게 같은 코드에 이어지는
경우)이 깨졌다. 두 경우를 실제 토큰 스트림에서 비교해보니 **완전히 같은 모양**이다
- "마이너스옵션"도 "드레스룸"도 똑같이 "직전 행의 마지막 숫자들 바로 다음에 오는
순수 한글 단어"다. 토큰 단위 규칙만으로는 이 둘을 구분할 근거가 없다는 걸
직접 확인했고, 안전하게 일반화하려면 지금은 공백 토큰화 과정에서 버려지는 줄바꿈

되돌렸다(회귀 없음, 코드는 원래 상태 유지). 이런 다항목 카탈로그형 옵션표를 쓰는

## 18차: "요약 탭 오피스텔 평당가가 계약면적 기준" + "이자후불제인데 중도금이 반영 안 됨" 제보 추적

사용자가 두 가지를 제보했다: ① 요약 탭에서 오피스텔 평당가가 계약면적 기준으로
나온다, ② 이자후불제 단지도 엑셀에 중도금(이자)이 반영 안 되는 이유를 확인해서
고쳐달라. 추가로 "프로그램과 엑셀의 차이, 내부 계산/시스템 오류를 모두 확인해서
고쳐달라"는 포괄적 요청도 있어 관련 코드 경로를 폭넓게 감사했다.

### ① 요약 탭 평당가 기준 불일치

`renderSummary`의 `pyeong = t.supply_area * 0.3025`가 `unit.kind`를 전혀 보지
않고 항상 `supply_area` 기준이었다. 엑셀 내보내기(`buildBlock`)는 13차에서 이미
"아파트=공급면적, 오피스텔=전용면적" 기준으로 고쳤는데, 요약 탭은 별도 계산
경로라 그 수정이 반영되지 않은 채 남아 있었다 - 오피스텔의 `supply_area`
필드는 실제로는 계약면적(전용+공용)이라, 요약 탭 평당가가 엑셀보다 낮게(계약
면적이 전용면적보다 크므로) 표시됐다. `isOfficetel ? t.exclusive_area :
t.supply_area`로 고치고, 타입 헤더의 면적 표기 문구와 "수정" 탭의 면적 입력
라벨도 어느 값이 평당가 분모인지 드러나도록 함께 갱신했다.

### ② 수정 탭 저장 시 회차별 중도금 실납부액이 사라지는 회귀

먼저 `isInterestFree`(이자 무료 여부 판정) 로직 자체를 의심했지만, 코드를 보니
`unit.interest === '무이자'` 조건은 처음부터 정상이었다 - "이자 후불제"는
`isInterestFree`가 false가 되어 정상적으로 이자 계산 수식이 들어가는 경로였다.
Playwright로 실제 단지를 등록한 직후 `units[0].types[0].rows[0]`을 찍어보니
`mid_amounts`(회차별 중도금 실납부액, 파서가 원문 공급금액표에서 읽어 옴)가
정상적으로 채워져 있었다 - 그런데 "수정" 탭에서 아무 값이나 하나 고치고
저장한 뒤 같은 걸 다시 찍어보니 `mid_amounts`가 통째로 사라져 있었다.

원인은 `saveEdit()`의 행 데이터 재구성 부분:
```js
t.rows = Array.from(tbody.querySelectorAll('tr')).map(tr => {
  const inputs = tr.querySelectorAll('input');
  return { dong: ..., floor: ..., units: ..., price: ... }; // mid_amounts 없음
});
```
"수정" 탭의 층별 표에는 동/층/세대/분양가 입력칸만 있고 회차별 중도금 자체는
편집 대상이 아닌데, 저장할 때 그 입력칸에 있는 값만으로 `t.rows`를 통째로
새로 만들어버려 입력칸에 없는 `mid_amounts`가 그냥 버려졌다. **단지를 등록한
뒤 수정 탭에서 무엇을 고치든(금리를 바로잡거나, 이자 조건을 "이자 후불제"로
명시하거나, 비고만 입력하거나) 저장 버튼을 한 번이라도 누르면 그 단지의 엑셀
중도금 이자가 전부 0으로 빠지는** 구조적 결함이었다 - "이자후불제인데 반영이
안 된다"는 제보의 실제 원인이었다(이자 조건 자체는 무관했고, 사용자가 거의
반드시 거치는 "수정 탭에서 확인 후 저장" 동작 자체가 트리거였다).

**수정**: 저장 직전의 `t.rows`(기존 값)를 `(동,층)` 키로 인덱싱해두고, 새로
만드는 각 행에 같은 키의 기존 `mid_amounts`를 이어받게 했다. 단순히 배열
인덱스로 이어받으면 행을 중간에서 삭제했을 때(`delRow`) 그 뒤 행들의 DOM
순서가 하나씩 밀려 엉뚱한 행에 잘못 붙을 수 있어, 내용(동/층 값) 기준 매칭을
우선하고 못 찾을 때만(동/층 텍스트 자체를 고친 경우) 인덱스로 대체하게 했다.
Playwright로 직접 행을 하나 삭제하고 저장해 남은 행들의 `mid_amounts`가
올바른 행에 유지되는지도 확인했다(회귀 없음). 원문에 없던 새 행을 사용자가
직접 추가한 경우는 매칭될 원본이 없어 빈 배열(이자 0)로 남는다 - 모르는 값을
지어내지 않는다는 원칙 그대로다.

### 부수 발견: 수정 탭에서 중도금 납부일을 직접 입력할 때 정확히 6개가 아니면 무시됨

## 19차: 엑셀 서식 다듬기(소계/합계 행 전체 배색, 가운데 정렬, 청약현황 테두리, 단지명 배경색 분리)

노란색 + 소계에도 전용/공급면적 평균(평형합계·합계와 동일하게), 평형합계·합계

③ 테두리 보강(경쟁률 파트 아래 등), ④ 3행 단지명 배경색을 오피스텔=자주 강조4

### ① 소계/평형합계/합계 행 전체 배색 + 소계 행 평당가 분모 추가

기존 코드를 보니 소계/평형합계/합계 행 모두 라벨(A열)·세대수(H열)·가중평균
(I~S열)이 있는 칸에만 색이 있고, 그 사이 칸(B,D~G열 등)은 흰 칸으로 비어
"줄무늬"처럼 보였다 - "A~S행 전체"라는 사용자 표현이 정확히 이 문제를 가리켰다.
`fillSummaryRow(fill, border)` 헬퍼를 새로 만들어 각 행 처리 맨 앞에서 A~S를
통째로 칠하고, 그 뒤에 오는 개별 라벨/수식 쓰기는 그대로 둬(같은 색/테두리를
다시 쓸 뿐이라 시각적으로 달라지지 않음) 순서 문제 없이 적용했다.

소계 행에 평당가 분모(C열)가 없었던 것도 확인 - 평형합계·합계는 이미 여러
타입을 가중평균한 C열 값을 보여주는데 소계만 비어 있었다("평형 합계 및
합계와 동일하게"라는 요청이 정확히 이 격차를 가리켰다). 한 타입 안에서는
C열이 항상 상수이므로(A~E 세로 병합의 이유와 동일) 그 타입 첫 행을 그대로
참조(`=C{ds}`)하는 것으로 충분했다.

### ② 경쟁률 파트 등 청약현황 블록 중간의 테두리 공백

"경쟁률 파트 아래 테두리"라는 예시를 단서로 살펴보니, 청약현황 블록(20~28열)
중 T(20)/AB(28)의 표 전체 관통 medium 구획선을 빼면 21~27열(경쟁률 포함)은
소계/평형합계/합계 행에서 테두리도 배경색도 전혀 없었다. 배경색은 그 블록이
메인 표(A~S)와 별개 구획이라는 기존 설계를 존중해 칠하지 않되, 21~27열에
나머지 열과 같은 상/하 테두리만 이어줘 "경쟁률 칸 아래가 뻥 뚫려 보이는"
끊김을 없앴다. T/AB의 구획선 전용 칸은 참고 서식 예시(17차에서 확인)대로
손대지 않았다.

### ③ "모든 셀 가운데 정렬"을 코드로는 이미 하고 있었는데 실제 파일엔 반영 안 됨 - ExcelJS 함정

코드의 `AC` 정렬 상수는 처음부터 `{horizontal:'center', vertical:'center', ...}`
였다. 그런데 실제로 다운로드한 파일을 다시 열어 `cell.alignment`를 확인해보니
`vertical`이 아예 없었다(가로만 가운데, 세로는 기본값인 "아래쪽"으로 렌더링).
ExcelJS 소스(`alignment-xform.js`)를 직접 열어보고서야 원인을 확인: ExcelJS가
받아들이는 세로 정렬 값 목록은 `['top','middle','bottom','distributed',
'justify']`이고 **`'center'`는 없다** - 유효성 검사에서 `'center'`가
`undefined`로 걸러지고, `undefined` 값은 아예 XML에 안 써진다. 즉 처음부터
이 프로젝트의 모든 "가운데 정렬" 셀이 세로로는 한 번도 진짜 가운데 정렬된 적이
없었던, 이번 요청 덕분에 처음 발견한 잠복 버그였다. `vertical:'middle'`로
고치고, `setCell`이 정렬을 안 받은 호출(테두리만 채우는 border-only 호출 등)도
기본으로 `AC`를 적용하도록 해 "모든 셀"이라는 요구를 그대로 만족시켰다.

### ④ 단지명 제목 배경색 - 아파트/오피스텔 분리

"오피스텔은 자주 강조4, 아파트는 주황 강조6"이라는 표현으로 미루어(강조4=
자주/보라, 강조6=주황은 Office 2013+ 기본 테마가 아니라 Office 2007-2010
테마의 배색과 일치 - 기본 테마의 강조4/6은 각각 금색/초록이라 순서가 다르다)

(오피스텔)/`FFFAC090`(아파트)을 얻었다. 계산값이 실제 Excel 표준 색상표에서
자주 인용되는 "Orange, Accent6, Lighter 40% = FAC090"과 정확히 일치해
공식과 테마 선택 모두 교차 검증됐다.

**테스트**: `e2e_v65_excel_style_test.js`에 검증 추가(S16~S23) - 소계/평형
합계/합계 행이 B~G열까지 배경색으로 끊김 없이 채워지는지, 소계 C열에 값이

### PDF 뷰어(poppler-utils) 신설 - "원문을 직접 본다"는 새 검증 축

이 환경에 `pdftoppm`(poppler-utils)이 아예 없어서 Read 도구의 PDF 페이지
렌더링 기능이 처음부터 동작하지 않았다는 걸 이번에 처음 발견했다(그동안은
pdfjs-dist로 뽑은 텍스트만 보고 표 구조를 추정해야 했다 - 즉 "파서가 보는
것"과 "사람이 실제로 보는 원본 레이아웃" 사이에 검증 격차가 있었다).
`apt-get install poppler-utils`로 설치하니 즉시 PDF 페이지를 이미지로 볼 수
있게 됐고, 이후로는 각 문서의 실제 표 페이지를 먼저 눈으로 확인해 정답을
파악한 뒤 파서 결과와 대조하는 방식으로 검증했다 - 이 라운드에서 찾아낸
실패 대부분이 "표 구조를 pdfjs 텍스트만 보고는 알아채기 어려운" 종류였다.

### 발견하고 고친 실패 (parser.js, 일반화된 방식으로 반영)

1. **레터 접미사형과 무접미사 관리코드형이 한 표에 섞임**(의왕역 SK VIEW) -
   `036.9653`처럼 문자 접미사가 없는 코드는 순수 면적값과 형태가 같아 기존
   정규식만으로는 구분 불가. "이 값이 몇 토큰 뒤 전용면적으로 그대로 반복
   등장하는지" 자기참조로 검증하는 `findSelfConsistentBareCodeBoundaries` 추가.
2. **"합계" 행 뒤 부가 표(주택형 표시 안내 등)가 코드를 다시 나열**(의왕역
   SK VIEW, 부산 장안지구) - 마지막 타입 구간이 합계 행/부가 표까지 삼킴.
   합계 행 이후 경계는 필터링.
3. **부가세 면제 행의 "-" 표기**(의왕역 SK VIEW, 오산헤리티지자이) -
   "대지비+건축비+부가세=합계" 산술 검증이 "-"에서 막혀 컬럼 구조를 통째로
   못 찾음. 금액 자리에서만 "-"를 0으로 취급.
4. **표 중간에 안내문이 끼어 뒷부분 행이 밀림**(부산 장안지구) - "■
   공통사항"이 pdf.js 재구성 순서상 표 중간에 끼어들어 59B 후반부/84A/84B
   행이 밀려남. area 코드 커버리지로 감지해 복구하는
   `repairFragmentedPriceTable`/`repairFragmentedAmountSection` 신설(price/
   balcony/option 공용, 복구 후 실제로 개선될 때만 채택 - 명시적 실패 원칙 유지).
5. **"공고일은 ~습니다" 서술형**(부산 장안지구) - 라벨-값 사이 조사 지원.
6. **번호/단위표기 소제목으로 나뉘는 다항목 옵션 카탈로그**(춘천 리버뷰
   아이파크, 의왕역 SK VIEW) - 서로 다른 품목이 섞이면 "코드당 최솟값"
   전제가 깨져 엉뚱한 품목의 최저가가 섞임. 어느 품목이 맞는지 판단 근거가
   없어 첫 소제목만 채택하고 나머지는 명시적으로 포기.
7. **"구분 84A 84B... 비고"류 타입별 열거 카탈로그**(의왕역 SK VIEW) - 품목당
   타입별 금액이 열로 나열되는 표는 스캔에서 제외(`stripCatalogTables`)하되,
   그 표가 섹션의 유일한 내용일 때만 헤더-데이터 열 정렬 검증으로 복구

10. **번호만 있고 불릿 없는 옵션 대분류**(의왕역 SK VIEW, "8 추가
    선택품목") 뒤 첫 표 헤딩을 앵커로 사용.
11. **섹션 종료 경계 오탐** - "납부일정"이 표 제목 자체에도 흔해 종료

   변환(`longCodeToShortCandidate`)으로 별칭 인식.

   (리체Ⅰ·Ⅱ) - "10층(최상층 ...)"(층 표기 자체에 괄호)와 "최상층\n(107동

7. **동일 층, 다른 동/호 그룹의 세대수 숫자만 페이지 경계로 고립**(리체Ⅱ) -

8. **옵션 카탈로그가 페이지 경계에서 끊기고 헤더 재인쇄 뒤 코드 재출현**

### 기준 파일 확정

첨부하며 "이 부분(T~AC) 다 삭제, 필요없어"라고 지정해 삭제 범위를 확정했다.

했다)/`cell.alignment`/`ws.merged_cells`/열너비/행높이까지 확인했다.

### 발견하고 반영한 구조

- 청약 현황 블록(구 T~AC)을 통째로 삭제 - 엑셀 열뿐 아니라 "수정" 탭의 관련

  `e2e_v65_subscription_fields_test.js`는 삭제.

  ("메인 표 끝+3열" 규칙 재적용). 이자표는 메인 헤더 서식(medium 강조,
  파란 배경)을 물려받지 않는 독립된 thin 상자로 정정.
- 회차별 일수(이자표 3행)를 하드코딩 숫자 대신 `=$입주일칸$행-회차날짜칸$행`

  외곽선으로 재정비. 금액 열(I~S)은 데이터/요약 행에서 오른쪽 정렬, A~H는
  가운데 정렬 - 단 헤더 행 라벨 자체는 금액 열이라도 가운데 정렬 유지(구현

## 23차: 실사례 5건 재현 - "PDF는 인식되는데 타입별로 전환이 안 된다" 문제 해결

22차와 함께 제기됐던 "PDF 인식은 되는데 타입별 분양가/확장비 등으로 전환이 안 된다"는
문제는 당시 재현 파일이 없어 미룬 상태였다. 이후 사용자가 실사례 PDF 5건을 첨부하며
"체크"를 요청해 Playwright로 각 문서를 실제로 첨부→분석해봤다. 3건은 이미 정상
동작했고, 2건(특히 "봉선동 르 오네뜨 2차")에서 타입 인식이 완전히 깨져 있는 걸
확인했다 - 이게 사용자가 말한 문제의 실제 사례였다.

### 발견하고 고친 실패 (parser.js, 일반화된 방식으로 반영)

- **약식표기가 표 셀 줄바꿈으로 코드 중간에서 쪼개짐** - "130A1"이 원본 표에서
  "130"과 "A1"이 서로 다른 줄에 걸쳐(칸이 좁아 줄바꿈) 텍스트 추출 시 공백으로만
  남으며 별개 토큰이 됐다. 코드 인식 정규식은 한 토큰 안에서만 매칭하므로 아예
  코드로 인식하지 못하고, "130A1"/"130A2" 두 타입이 최후수단 규칙(인접 정수를 코드로
  대신 쓰는 폴백)에 의해 "130" 하나로 뭉개지며 세대수도 나중 값이 앞 값을 덮어썼다
  (28+26=54인데 26만 남음). 중도금 회차 인식도 이 여파로 코드셋이 깨지면서 통째로
  0/6이 됐다. `reglueSplitShortCodes()`를 추가해, "숫자 토큰+문자 접미부 토큰"이
  근처(다음 몇 토큰 안)에 같은 정수부를 가진 실수(전용면적 등, 이 숫자가 실제로 그
  타입의 코드라는 구조적 증거)로 검증될 때만 재결합하도록 했다(우연한 숫자+글자
  나열까지 잘못 합치지 않도록).
- **발코니/옵션 소제목이 대괄호형("[단위 : 원, VAT 포함]")** - 20차에서 도입한 "첫
  소제목만 남기고 나머지는 버린다"는 안전장치(`restrictToFirstUnitMarkerSubsection`)가
  괄호("(단위: ...)")만 인식하고 대괄호는 인식하지 못해, 첫 소제목 뒤에 이어지는 완전히
  무관한 두 번째 소제목(코드 없는 개별품목 카탈로그)의 값이 코드에 잘못 붙었다(예:
  130A2의 옵션가가 시스템에어컨 12,700,000 대신 엉뚱한 침실 붙박이장 2,800,000으로
  나옴). 괄호/대괄호 둘 다 인정하도록 정규식을 넓혔다.
- **"구분" 헤더의 글자 사이 공백("구 분")** - 같은 문서의 "계 약 금"/"중 도 금"처럼
  PDF 추출 시 한글 단어 중간에 공백이 끼는 문제가 카탈로그형 표 판별 키워드 "구분"에도
  있어 `stripCatalogTables`/`extractColumnAlignedCandidates`가 해당 표를 인식하지
  못했다. 공백 유무와 무관하게 인식하도록 넓혔다.

### "130A1/130A2가 가격표를 공유한다"는 사용자 확인 후 재작업

처음엔 무작위 배정으로 "130A1\n130A2" 두 코드가 같은 가격표를 공유하는 구조(같은
주택형에 속하고 동·호수가 랜덤 배정돼 가격도 동일 - 공고문 원문에도 "무작위
배정되오니"라고 명시돼 있었다)까지 반영하려고 `scanPriceRowsWithMap`에 "연속된
코드는 같은 행 세트를 공유한다"는 그룹 누적 로직을 추가했으나, 기존 회귀 스위트에서
2건이 깨져(H03: "059.0000A"라는 그룹 코드가 별칭 변환 규칙상 우연히 "59A"와
같아지며 뒤따르는 "59AL"과 잘못 묶임 / O04: "84B 84C" 매핑 안내 줄이 실제 가격
데이터 없이 코드만 나열된 것뿐인데 공유 그룹으로 오인됨) 일단 되돌렸었다(130A1이
가격 데이터 없이 ⚠ 경고로만 표시됨).

이후 사용자가 "130A1과 A2가 동일한 분양가로 나온 거야, 둘이 같아"라고 직접 확인해줘
다시 붙였는데, 이번엔 "코드가 나란히 언급된다"는 형태 신호 대신 **"이 코드가 가격
섹션 전체에서 정확히 한 번만 등장하는가"**를 판단 근거로 삼았다. 진짜 공유 그룹의
코드(130A1/130A2)는 그 공유 지점 딱 한 번만 나오고 그 뒤 데이터는 코드 없이 층
정보만으로 이어지는 반면, H03의 "59A"(별칭 충돌)나 O04의 "84B"/"84C"(안내문)는
나중에 자기 이름으로 시작하는 별도의 데이터 블록을 또 갖기 때문에 최소 두 번 이상
등장한다 - 이 등장 횟수 차이로 세 사례가 전부 안전하게 구분된다(별칭으로 해석된
코드는 이 판단 자체가 무의미하므로 애초에 공유 후보에서 제외). `test_cases_q.js`에
Q07(130A1/130A2 각각 6개 행·세대수 합계 54를 그대로 공유하는지)을 추가해 고정했다.

실제 PDF 5건을 Playwright로 첨부→분석까지 돌려 원문과 직접 대조했다.

## 24차: 진월동지역주택조합 - 페이지 경계에서 타입 하나가 통째로 유실

받아 확인해보니: 공급금액표가 84D 타입 중간(페이지 8→9 경계)에서 끊기고, pdf.js 재구성
순서상 그 사이에 완전히 무관한 "■ 특별공급 공급세대수" 표와 "■ 공통 유의사항" 안내문
여러 줄이 끼어든 뒤에야 84D의 마지막 행("14층\n(최상) 1 338,283,000...")과 115 타입의
코드 헤더("115 109동 1호, 2호")가 이어졌다.

### 발견하고 고친 실패 (parser.js, 일반화된 방식으로 반영)

이런 "표 중간에 무관한 섹션이 끼어드는" 문제 자체는 20~21차에서 이미 여러 건 다뤘고
전용 복구 로직(`repairFragmentedPriceTable`/`repairUndercountedPriceRows`)도 있었지만,
그 복구 로직 자체에 있던 두 가지 결함이 겹쳐 이번엔 복구가 실패했다:

- **`mergeWrappedFloorLines`의 `matchesResume` 판단 순서가 거꾸로였다** - "14층\n(최상)
  1 338,283,000..."처럼 층 표기와 실제 숫자 사이를 괄호 부연설명이 완전히 가로막고
  있으면, 괄호를 지우기 전(원문 그대로)에는 "층" 바로 뒤가 공백이 아니라 "("라 영원히
  매칭될 수 없다. 그런데 기존 코드는 "원문이 이미 매칭돼야" 그다음에 괄호 제거 버전도
  확인하는 순서였다(`if (!resumeRe.test(s)) return false; return resumeRe.test(stripped)`) -
  원문이 매칭될 수 없는 이 경우엔 괄호 제거 버전 확인 자체를 못 가보고 항상 실패했다.
  판단을 괄호 제거 버전 하나로 단순화했다(괄호 안 내용은 지워지고 없으니 "괄호 안 숫자에
  우연히 매칭"될 걱정도 자연히 사라진다).
- **`repairFragmentedPriceTable`의 재개 지점 탐색 정규식이 너무 좁았다** - "층 표기 바로
  뒤에 공백만 있고 곧장 숫자가 오는" 한 줄짜리 패턴(`[ \t]+\d`)만 인정해서, 위 병합 함수를
  고쳐 한 줄로 합쳐놔도 "14층 (최상) 1 338,283,000..."처럼 괄호가 포함되면 여전히
  매칭되지 않았다. 그러면 이 줄을 건너뛰고 그다음(엉뚱하게 더 늦은) 매칭인 "1층 2
  359,530,000..."(115의 첫 데이터 행)에서 재개해버려, 건너뛴 84D의 마지막 행과 그 사이의
  "115 109동 1호, 2호" 코드 헤더가 통째로 사라졌다. 그 결과 115의 네 행은 코드 없이
  이어지다 직전 코드(84D)에 잘못 흡수되어(84D는 9세대인데 16세대로 과다집계, 115는 아예
  0/8) 진단됐다. `repairUndercountedPriceRows`가 이미 쓰고 있던 "층 표기 뒤에 숫자·개행만
  아니면 무엇이든(괄호 부연설명 포함) 허용"하는 정규식(`[^\d\n]*\d`)으로 통일했다.

수정 전 이 두 함수를 순서대로 디버깅하며 확인한 흐름: `repairFragmentedPriceTable`이
호출은 되지만 `mergeWrappedFloorLines`가 "14층"과 "(최상) 1 338,283,000..."을 병합하지
못해 그대로 두 줄로 남고, 이어서 재개 지점 정규식이 이 두 줄을 각각 매칭 시도하다 실패,
결국 그다음 매칭 가능한 지점(115의 첫 행)에서 재개하며 문제가 발생했다.

### 검증 방법

84D/115/126 여섯 타입 전부 표기 세대수와 정확히 일치하는지). 원인이 두 복구 함수의
정규식/판단 로직 자체에 있었으므로, 같은 로직을 쓰는 기존 실사례(부산에코델타시티/

## 25차: 단지별 요약본(AF~AK) 신규 추가

사용자가 "단지별 요약본 추가하려고 하는데 AF~AK열 부분 참고해서 요소 하나하나 파악해서
그대로 넣어서 작성해줘"라며 실사용 예시 파일(메인 표와 같은 시트, 각 단지 데이터 시작행
부터 AF~AK열에 붙는 타입별 요약 표가 이미 5개 단지분 채워진 문서)을 첨부했다. openpyxl로
값·수식·서식을 전부 뜯어봐 반영했다.

### 구조 파악

- 위치: 각 단지의 메인 표 데이터 시작행(제목행+5)부터 AF열에 시작.
- 1행(단지명=메인 표 제목 실시간 참조 + "*공급평형기준") → 2행(사용승인일 + 총 세대수) →
  헤더 2행 → 타입별 요약 행들 → 맨 아래 "평균" 행.
- 각 요약 행은 메인 표의 이미 계산된 셀을 그대로 참조한다(전용(평)=`A{데이터시작행}*0.3025`,
  공급(평)=`C{데이터시작행}`, 세대수=`H{소계행}`, 분양가=`I{소계행}/10000`(만원 단위),
  평당가=분양가/공급평).

### 발견한 핵심 - 타입 묶음 기준이 메인 표와 다르다

메인 표의 "OO합계"는 약식표기의 숫자 접두부가 같아야 묶이는데, 이 요약본은 그 기준으로
설명이 안 되는 묶음이 여러 군데 있었다(예: "102"와 "124"가 한 그룹, "115"와 "126"이 한
그룹 - 접두부가 서로 다름). 각 타입의 실제 전용면적(A열)에 0.3025를 곱해 평형으로
환산해보니, **전용평수를 10평 단위로 내림한 "평형대"가 같은 타입끼리 묶인다**는 게
드러났다(102→31.15평→30평대, 124→37.5평→30평대 - 일치). 예시 파일 5개 단지 전체를
이 기준으로 재검증해 예외 없이 들어맞는 걸 확인한 뒤에야 구현에 들어갔다 - 처음
발견했을 때는 "그냥 수기로 대충 짝지은 것 아닌가" 의심했지만, 독립된 5개 단지 데이터가
전부 하나의 산술 규칙으로 설명돼 실제 의도된 기준임을 확신할 수 있었다.

- 평형대 타입이 하나뿐이면 그 타입 행 + 자기 값을 그대로 반복하는 마감행(옅은 주황) 2행.
- 둘 이상이면 타입별 행 + 세대수 가중평균 마감행(옅은 주황) 1행.
- 맨 아래 "평균" 행(옅은 빨강)은 항상 각 평형대의 마감행만 참조 - 단일/그룹 여부와 무관하게
  참조 지점이 균일하도록 설계돼 있었다(다행히 마감행을 "그 평형대의 최종 대표값"으로
  통일한 덕분에 평균 행 수식 하나로 모든 케이스를 커버).

### 의도적으로 예시와 다르게 반영한 부분

- 예시의 "총 N 세대수"는 하드코딩 텍스트였지만, 이 프로젝트는 값을 하드코딩하지 않고
  항상 수식으로 참조해 편집에 따라 갱신되게 하는 원칙이라 그 단지 합계 행(H열)을 실시간
  참조하는 문자열 결합 수식(`="총 "&H{tr}&" 세대수"`)으로 바꿨다.
- 예시의 두 번째 단지("2-2BL") 평균 행에서 AG/AH열이 첫 번째 단지("2-1BL")의 행 번호를
  그대로 복사해온 명백한 복사·붙여넣기 오류를 발견했다(같은 행의 AI/AJ/AK열은 정상적으로
  자기 단지 행을 참조하고 있어서 대조가 가능했다). 오류를 그대로 베끼지 않고 정상 열과
  같은 패턴(그 단지 자신의 마감행 참조)으로 통일했다.

### 발견하고 고친 실패 (parser.js, 일반화된 방식으로 반영)

**목동윤슬자이 오피스텔(서울 양천구)**

- **area 앵커가 "공급면적" 문구를 못 받음** - 기존엔 "공급대상"류 문구만 인식했는데, 이
  문서는 "■ 공급면적 및 공급규모"를 쓴다. `SECTION_ANCHORS.area`에
  `[■▣]\s*공급면적\s*(?:및\s*공급규모)?` 패턴을 추가했다(■/▣가 바로 앞에 붙는 진짜
  제목줄만 앵커로 삼으므로, 본문 산문에 그냥 단어로 등장하는 "공급면적"과는 오탐 없이
  구분됨을 두 문서 전체 grep으로 확인).
- **price 앵커가 "납부 일정"(글자 사이 공백)을 못 받음** - "■ 공급금액 및 납부 일정"처럼
  PDF 추출 과정에서 한글 단어 중간에 공백이 끼는, 이미 여러 차례 확인된 문제와 같은
  종류(구분→구 분, 계약금→계 약 금 등). `납부일정`을 `납부\s*일정`으로 완화했다.
- **하이픈 뒤에 숫자까지 붙는 코드를 못 받음** - `117C-T1`/`118C-T2`/`119A-T1`/
  `120A-T2`/`120A-T3` 5개 타입이 아예 인식되지 않았다. 기존 `SHORT_CODE_RE`의 하이픈
  접미사 그룹이 문자만 허용(`-[A-Za-z]{1,3}`)했는데, 숫자까지 붙는 그룹
  (`-[A-Za-z]{1,3}\d{0,2}`)으로 넓혔다(기존 동기 사례 "84E1-T"는 숫자가 0개이므로
  그대로 매칭됨을 확인).
- **area 표 총계행 뒤 별개 요약표가 세대수를 오염시킴** - area 표가 진짜 총계행("계 651
  -")으로 끝난 뒤, 완전히 별개의 "■ 거주자 우선 분양" 표가 같은 타입 코드를 전부 다시
  나열하며 자기 "합계" 행으로 끝난다. 기존 총계행 판별은 "마지막 경계(lastBoundary,
  =전체 텍스트에서 코드가 가장 마지막으로 등장하는 위치) 이후에 나오는 '계'+숫자만
  총계로 인정"했는데, 이 `lastBoundary`가 뒤쪽 요약표 안의 코드 위치를 가리켜버려 진짜
  총계행("계 651")은 기준을 통과 못 하고, 대신 요약표의 "합계"(위치 무관하게 무조건
  매칭되는 첫 번째 정규식 분기)가 컷오프로 잘못 채택됐다. 그 결과 진짜 표와 요약표
  경계가 둘 다 살아남아 뒤섞이며 `203AD`가 실제 10세대 대신 20세대로 두 배 집계됐다.
  "마지막 경계" 대신 "모든 코드가 최초로 한 바퀴 다 나온 시점(firstFullBoundary)"을
  기준으로 바꿔, 뒤쪽 요약표를 기다리지 않고 진짜 표의 총계행에서 멈추도록 고쳤다(단일
  표만 있는 기존 실사례에서는 두 값이 항상 같아 회귀 없음).
- **"최저가/최고가" 두 행짜리 가격 범위 표 - 세대수 컬럼 자체가 없는 신규 구조** - 이
  문서의 price 표는 층별 행이 아예 없고, 타입마다 "최저가"/"최고가" 딱 두 행만 있으며
  세대수 칸조차 없다(타입 전체 세대수는 코드 바로 뒤 헤더 줄에 한 번만 나옴, 예: "1군
  115A 118"). 기존 `pushRow`는 세대수 없는 행을 세대수 1로 기본 처리하므로, "최저가"를
  순수 한글 라벨로 오인해 1세대, "최고가"도 1세대 - 타입당 2세대로 심하게 과소집계됐다.
  최저가/최고가 사이에 세대수를 어떻게 나눠야 하는지는 문서 어디에도 없으므로(지어내면
  "실사례에 없는 값을 지어내지 않는다" 원칙 위반), 코드 뒤에 층별 행 없이 세대수 하나 +
  "최저가"/"최고가" 두 행만 오는 패턴을 전용 분기로 인식해 두 값을 항목별(대지비/건축비/
  부가세/계약금/중도금 회차/잔금 각각)로 평균한 행 하나로 합치고, 세대수는 헤더의
  타입 전체 값을 그대로 썼다. 각 항목이 같은 비율 구조(대지비+건축비+부가세=계, 10/60/30
  분할)라 항목별 평균의 합이 총액 평균과도 일치해 내적 일관성이 유지됨을 확인.

**송도국제도시 B1블록 대방디엠시티 오피스텔(인천 연수구)**

- **번호+")" 옵션 챕터 헤딩을 못 받음** - "▣ 별도옵션 품목 및 계좌, 납부방법" 뒤에 "1)
  FCU / 2) 추가선택사항 옵션품목 / 3) 추가선택사항 유의사항" 세 줄이 목차로만 나열된다.
  기존 `CHAPTER_NUMBER_OPTION_RE`는 번호 뒤 ")"/"."를 허용하지 않았고 "사항" 같은
  임의 삽입어도 못 받아서 "2) 추가선택사항 옵션품목"에 매칭되지 않았다. 부산에코델타시티
  사례에서 이미 쓰던 "추가 + 임의 0~6자 + 옵션품목" 관대한 사이 구간 패턴을 그대로
  재사용해 번호 뒤 punct까지 허용하도록 넓혔다.
- **매칭되어도 실제 표를 통째로 건너뜀** - 챕터 헤딩을 인식해도, 기존
  `findChapterFirstHeading`은 "다음 ■/▣ 헤딩까지 무조건 건너뛰기"만 했다. 이 문서는
  실제 옵션 표가 챕터 헤딩 바로 뒤에 자기만의 ■/▣ 헤딩 없이 곧장 이어지는데, 문서 훨씬
  뒤(수십 줄 뒤)에야 나오는 무관한 "▣ 계약조건 및 유의사항"까지 건너뛰어버려 진짜 표
  자체가 옵션 섹션에서 통째로 빠졌다(실측: `sections.option`이 "▣ 계약조건 및
  유의사항"부터 시작). 챕터 헤딩 바로 뒤에 같은 목차 나열의 형제 번호줄("3) 추가선택사항
  유의사항")이 곧장 이어지면 그 목차 블록 끝까지만 건너뛰도록 고쳤다(형제 줄이 없으면
  기존대로 다음 실제 헤딩까지 건너뛰어, 헤딩과 표 사이에 무관한 산문이 낀
  부산에코델타시티류 문서는 그대로 유지).
- **옵션 표 뒤에 이어지는 별개 카탈로그가 마지막 타입의 옵션가를 오염시킴** - 위를 고쳐
  옵션 표를 올바르게 찾아도, 그 표 바로 뒤에 코드 반복 없이 "전 주택형" 공통 품목만
  나열되는 별개의 가전/가구 카탈로그("항 목 타입 품목명 옵션금액 계약금 잔금 비 고")가
  헤더 구분 없이 곧장 이어졌다. `scanAmountGroups`의 "코드가 마지막으로 등장한 뒤 나오는
  순수 한글 단어는 그 코드의 연속행"이라는 규칙(원래는 같은 타입의 서브옵션 라벨 대응용)이
  이 무관한 카탈로그의 한글 단어에도 그대로 적용되어, 마지막으로 언급된 코드(84OB)의
  후보 금액 목록에 카탈로그 안의 무관한 최소값("세탁기 하부장 300,000")까지 섞여 들어가
  최종 채택값(최솟값)이 84OB 자기 표의 2,000,000 대신 300,000으로 잘못 뭉개졌다.
  "타입"과 "품목명"이 나란히 컬럼 헤더로 나오는 줄이 보이면 그 지점부터는 "코드당 값
  하나"라는 전제와 안 맞는 별개의 표로 보고 그 이전까지만 남기는
  `restrictBeforeItemCatalogHeader`를 `restrictToFirstNumberedSubsection`/
  `restrictToFirstUnitMarkerSubsection`과 같은 자리에 추가했다(이 두 함수도 "여러
  품목이 섞인 카탈로그는 첫 품목만 신뢰하고 나머지는 명시적으로 포기"라는 같은 원칙).
